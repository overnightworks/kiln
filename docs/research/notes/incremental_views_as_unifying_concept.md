# Incremental View Maintenance as a Unifying Concept (indexes / caches / materialized views / subscriptions)

Scope note: this covers "part 2" of the candidate idea — unifying indexes, caches, materialized views, and live subscriptions as one mechanism ("every known query = an incrementally maintained, possibly parameterized view"). Confidence levels are given per claim as **[High]** (directly stated by a primary source), **[Medium]** (stated by a credible secondary source / vendor doc, not cross-checked against the primary paper), or **[Low]** (inferred by the researcher, not directly stated anywhere found).

## What do Noria, ReadySet, DBSP/Feldera, Materialize/DD/Timely, Convex, Electric SQL, RisingWave, pg_ivm, and Oracle/SQL Server indexed views do?

### Takeaway
All of these systems implement some form of incremental (delta-based) view maintenance, and several explicitly fuse "index" and "materialized view" into one internal mechanism (arrangements in Materialize/Differential Dataflow; partially-stateful operators in Noria). None of the surveyed systems is both (a) a general-purpose closed-world workload compiler that maintains *every* query as a parameterized IVM view and (b) embedded inside a transactional OLTP storage engine with views updated in the same serializable transaction as writes to base data — the two things get traded off against each other across the field.

### Cited Findings
- **Noria (OSDI 2018)**: a dynamic, partially-stateful dataflow system. It "executes queries in response to writes" rather than reads, turning reads into index lookups into precomputed state; it supports adding new queries while running, extending the live dataflow graph, and shares state/computation across related queries instead of duplicating it. — [USENIX OSDI'18 paper](https://www.usenix.org/conference/osdi18/presentation/gjengset); [NSF PAR copy](https://par.nsf.gov//servlets/purl/10129101)
- Noria's **partial state**: operators can hold only a subset of records; missing entries are filled lazily via recursive **"upqueries"** that walk back to base tables (or upstream stateful operators) on a read miss, but only where an upquery can be answered by an efficient index lookup — if it would require a full scan of upstream state, partial state is disabled for that operator entirely (it falls back to full materialization). — [acolyer.org summary of OSDI'18 paper](https://blog.acolyer.org/2018/10/29/noria-dynamic-partially-stateful-data-flow-for-high-performance-web-applications/)
- Noria **eviction**: under memory pressure, partially-materialized entries are evicted like a cache; eviction notices propagate along the dataflow so downstream operators know those entries will stop being kept current. The exact eviction policy (e.g., LRU) is not stated in the secondary source found. — [acolyer.org](https://blog.acolyer.org/2018/10/29/noria-dynamic-partially-stateful-data-flow-for-high-performance-web-applications/)
- Noria **consistency**: writes land in durable base tables and propagate through the dataflow graph; the guarantee given is **eventual consistency** — once writes quiesce, views match what a direct query against base tables would return. Correctness requires deterministic operators, no update-reordering on a path, and commutative merging at multi-ancestor operators. — [acolyer.org](https://blog.acolyer.org/2018/10/29/noria-dynamic-partially-stateful-data-flow-for-high-performance-web-applications/)
- Noria **storage overhead**: roughly **3× the base-table size** measured on the Lobsters workload; a pure memcached+DB setup without persistence still beats Noria at ~100–200K req/s on read-heavy load (called an unrealistic comparison by the paper/summary because it ignores persistence). — [acolyer.org](https://blog.acolyer.org/2018/10/29/noria-dynamic-partially-stateful-data-flow-for-high-performance-web-applications/)
- Noria reports **5× the load** of a hand-optimized MySQL baseline for a real web application's query mix, and outperforms a MySQL/memcached stack and a commercial database's materialized views, per the paper abstract. — [USENIX OSDI'18 abstract](https://www.usenix.org/conference/osdi18/presentation/gjengset)
- Noria's **storage engine for base tables** is RocksDB; base tables are explicitly the *roots* of the dataflow DAG (sources of truth), not derived views — writes hit the base table first and then propagate as deltas. — [acolyer.org blog summary](https://blog.acolyer.org/2018/10/29/noria-dynamic-partially-stateful-data-flow-for-high-performance-web-applications/); [Cambridge ACS slide deck on Noria](https://www.cl.cam.ac.uk/~ey204/teaching/ACS/R244_2019_2020/presentation/S2/niall_NORIA.pdf) **[Medium — secondary sources agree, primary paper not directly read]**
- **ReadySet** (commercial product derived from Noria's ideas) is a wire-compatible caching layer that sits **downstream of** an existing Postgres or MySQL instance: it connects to the upstream DB, consumes its logical replication stream, and incrementally maintains a dataflow-graph cache for queries the operator opts in with `CACHE QUERY`. Non-cached queries are proxied straight through to the base database. Thoughtworks' Technology Radar describes its mechanism as "partial view materialization" giving lower tail latency than a traditional read replica. — [docs.readyset.io/concepts/overview](https://docs.readyset.io/concepts/overview); [Thoughtworks Radar entry](https://thoughtworks.com/radar/tools/readyset); [ReadySet behind PgBouncer blog](https://readyset.io/blog/a-deep-dive-on-readyset-behind-pgbouncer) **[Medium — vendor/third-party docs, not the OSDI paper itself]**
- **DBSP / Feldera**: the paper "DBSP: Automatic Incremental View Maintenance for Rich Query Languages" (Budiu, Chajed, McSherry, Ryzhyk, Tannen) won **Best Paper at VLDB 2023** (PVLDB vol. 16, pp. 1601–1614). It gives (1) a language for stream computations, (2) a new formal definition of IVM, and (3) a general, "heuristic-free" incrementalization algorithm that applies to arbitrary DBSP programs, claimed to cover SQL and Datalog alike. — [Feldera blog: Best Paper VLDB 2023](https://feldera.com/blog/Best-Research-Paper-VLDB-2023); [paper PDF](https://www.vldb.org/pvldb/vol16/p1601-budiu.pdf); [arXiv 2203.16684](https://arxiv.org/pdf/2203.16684)
- DBSP models data as **Z-sets**: elements carry integer multiplicities, negative multiplicities represent **retractions** (deletes); Z-sets form a group under addition, so negation gives deletion "for free," and updates are a −1 on the old value plus a +1 on the new value. Incremental join is bilinear: `(R ⋈ S)[(r,s)] = R[r] · S[s]`, so a change on either side produces a correctly-signed delta on the output automatically, including through joins and aggregates. — [arXiv 2203.16684 (DBSP paper)](https://arxiv.org/pdf/2203.16684); [Feldera blog: SQL on Z-sets](https://www.feldera.com/blog/SQL-on-Zsets/)
- DBSP explicitly extends coverage to **recursive queries**: it claims to handle monotonic *and* non-monotonic recursion, implementing stratified Datalog via a fixed-point circuit — contrasted with "earlier techniques built for restricted classes" that don't generalize. — [arXiv 2203.16684](https://arxiv.org/pdf/2203.16684); [VLDB listing](https://mail.vldb.org/pvldb/volumes/16/paper/DBSP%3A%20Automatic%20Incremental%20View%20Maintenance%20for%20Rich%20Query%20Languages) **[Medium — this is the authors' own claim about generality, not independently verified by a third party in this research pass]**
- Feldera's docs state **DBSP is not a database** — "DBSP is not designed to replace a standard database, but to work in conjunction with an existing one." It is a query engine, downstream of the system of record, not embedded in an OLTP storage engine. — [docs.feldera.com](https://docs.feldera.com/sql/intro/) (per WebSearch summary)
- **Differential Dataflow (DD) / Materialize**: DD's **arrangements** are indexed, incrementally-maintained collections: "the mechanisms that maintain materialized views are called arrangements." Materialize builds and keeps indexes on both input and output collections and on intermediate collections, keeps them in memory, and **shares a single arrangement/index across every query that needs the same keyed data** rather than rebuilding it per query — the "Shared Arrangements" paper (McSherry, Lattuada, Schwarzkopf, Roscoe) reports large gains in response time and resource use from this inter-query sharing. — [Materialize docs: Arrangements](https://materialize.com/docs/overview/arrangements); [Shared Arrangements paper](https://ar5iv.org/html/1812.02639)
- In Materialize's own docs, an **index** is described as a thing that "holds arranged data in memory," while a **materialized view** "saves query results" (persisted, durably stored, incrementally updated). The docs present indexes and materialized views as *two still-distinct object types* built on the same underlying incremental-dataflow machinery (arrangements) — they are not formally unified into a single user-facing concept, even though they share the implementation mechanism. When indexes already exist on the join keys for a multi-way join, Materialize can use a "delta join" that adds **no extra storage/memory cost** beyond those indexes. — [Materialize docs: Arrangements, fetched directly](https://materialize.com/docs/overview/arrangements) **[High — directly fetched from the primary doc]**
- **RisingWave**: materialized views are "incrementally maintained in real time" — on new input it "touches only the affected rows rather than recomputing everything," contrasted explicitly against traditional (batch, full-recompute) materialized views. Creating a view triggers a backfill plus installation of streaming operators (a DAG) that listen to upstream changes; views can cascade (built on top of other materialized views). It is wire-compatible with Postgres. — [RisingWave docs: What is a materialized view](https://docs.risingwave.com/reference/what-is-materialized-view); [RisingWave blog: Incremental MVs explained](https://risingwave.com/blog/incremental-materialized-views-explained/) **[Medium — vendor-authored sources]**
- **pg_ivm** (PostgreSQL extension, sraoss): supports **"immediate maintenance"** — materialized views ("IMMVs") are updated via `AFTER` triggers **within the same transaction** as the base-table write that caused the change. Usage requires calling `create_immv(...)` instead of `CREATE MATERIALIZED VIEW`. Recent work (PGConf.EU 2026 talk, Oct 2026) adds outer-join support and explores deferred maintenance. — [github.com/sraoss/pg_ivm](https://github.com/sraoss/pg_ivm); [PGConf.EU 2026 session](https://www.postgresql.eu/events/pgconfeu2026/sessions/session/8219-pg_ivm-recent-improvements-and-future-directions-in-incremental-view-maintenance/) — this is the **closest found example of IVM updated transactionally inside an OLTP engine** (it runs as a Postgres extension inside Postgres's own transaction machinery, so the view update is part of the same ACID/serializable transaction as the base write), though it is a bolt-on extension rather than the engine's native index/storage path. **[Medium — extension docs/talk abstracts, not an academic evaluation of its transactional isolation guarantees]**
- **Oracle / SQL Server indexed views / fast-refresh materialized views**: Oracle's **fast refresh** uses a separate **materialized view log** on the base table (recording row-level INSERT/UPDATE/DELETE since last refresh) to apply only the delta instead of a full re-execution ("complete refresh"). No source found describes Oracle treating a plain secondary index as a special case of this mechanism — the MV log is a distinct structure from a B-tree index, maintained alongside the base table similarly to how an index is maintained, but the sources explicitly addressing this (`USING INDEX` clause) only configure *the materialized view's own backing index's* storage parameters, not a unification of the two concepts. — [dbi-services blog: fast vs complete refresh](https://www.dbi-services.com/blog/oracle-materialized-view-refresh-fast-or-complete/); [Oracle docs on MV logs](https://docs.oracle.com/en-us/iaas/database-tools/doc/creating-materialized-view-log.html)
- **SQL Server indexed views** are heavily restricted relative to general materialized views: the defining query must be deterministic (e.g., no `GETDATE()`), must use `WITH SCHEMABINDING`, reference only base tables in the same database, and may **not** use `OUTER JOIN`, `EXISTS`/`NOT EXISTS`, subqueries, `TOP`, or `UNION`; aggregate views must select `COUNT_BIG(*)`. The outer-join restriction exists specifically because rows can "logically disappear" from an outer-joined indexed view on an insert to a base table, which the documentation says makes incremental maintenance harder and slower. — [SQL Server docs via sqlshack](https://www.sqlshack.com/sql-server-indexed-views); [sqlauthority.com on outer joins](https://blog.sqlauthority.com/2010/09/24/sql-server-outer-join-not-allowed-in-indexed-views-limitation-of-the-view-8/)
- **Convex reactive queries**: per Convex's own docs, queries are **not** incrementally maintained in the DBSP/differential-dataflow sense. Convex tracks the *read set* (dependencies) of each query function and **reruns the whole query function** when any of its dependencies changes, then diffs/pushes the new result to subscribed clients. A November 2025 change moved the "subscription worker" (which decides which queries need re-evaluation on a write) to a **treap-based** data structure, reported to cut CPU usage and tail latency — but this optimizes *which* queries get rerun, not *how* a query's result is incrementally recomputed. Convex uses serializable isolation / OCC underneath, giving subscriptions a consistent snapshot. — [Convex docs: Realtime](https://docs.convex.dev/realtime); [Convex changelog: treap subscription engine](https://ship.convex.dev/changelog/treap-subscription-engine-optimization)
- **Electric SQL** (rebranded "Postgres Sync" / Electric): a read-path sync engine, not a query engine. It consumes Postgres's **logical replication stream** and fans data out into **"Shapes"** — a shape = a table + optional `WHERE` + optional `columns`, delivered to clients as an append-only log of changes ("sorted by offset"); shapes are immutable once defined (can't be redefined) and are currently single-table. Client-side "live queries" can further narrow a shape. This is closer to a declarative, parameterized **cache/replica of row subsets** than to a general incrementally-maintained query (no joins/aggregates are incrementally maintained server-side; the compute happens on the client against the synced rows). — [electric-sql.com: Shapes guide](https://electric-sql.com/docs/guides/shapes); [electric.ax: Postgres Sync](https://electric.ax/sync/postgres-sync)

### Inferences
- Across the field there is a real split: systems that unify "index" and "materialized view" at the *implementation* level (Materialize/DD's arrangements, Noria/ReadySet's dataflow state) still expose them to the user as **separate objects** (`CREATE INDEX` vs `CREATE MATERIALIZED VIEW` in Materialize; "cached query" vs base-table access in ReadySet) rather than collapsing the *user-facing concept*. **[Low-Medium — inferred from the docs above, not a claim any source makes explicitly]**
- No surveyed system both (a) treats *every* query as a parameterized IVM view with no separate index concept at all, and (b) runs inside the OLTP engine's own transaction manager with serializable, same-transaction consistency. pg_ivm gets closest to (b) (same-transaction, inside Postgres) but is opt-in per view, not a wholesale replacement of indexing; Noria/ReadySet/Materialize/RisingWave get closer to (a) in spirit (broad dataflow-based materialization) but all sit **downstream** of, or **separate from**, a transactional OLTP engine of record (Noria owns its own RocksDB-backed base tables but is not a general-purpose transactional SQL engine with secondary indexes removed as a concept; ReadySet explicitly proxies around a separate upstream DB). **[Medium — this is the researcher's synthesis across the cited findings above]**

### Gaps
- No source found states explicitly, in so many words, "a secondary index is a special case of a parameterized materialized view, and we remove the index as a separate concept" for *any* system. The closest textual support is Materialize's docs language that indexes and materialized views are both built from "arrangements," but the docs still keep them as two user-level object types — this is the researcher's inference, not a direct quote.
- Could not access the full Noria OSDI'18 PDF or the MIT ;login: 2019 article as text (WebFetch returned only binary/PDF-stream content), so Noria's exact eviction policy (e.g., LRU vs frequency-based), and any explicitly stated limitations around joins/aggregates-with-deletes/recursive queries in the *primary* paper, were not independently confirmed — only the acolyer.org secondary summary was usable.
- Could not confirm from a primary/official ReadySet architecture page (the specific blog URL guessed returned 404) whether ReadySet makes an automatic, cost-based choice between caching a query and proxying it, versus requiring the operator to manually opt in via `CACHE QUERY`. The evidence found supports *manual* opt-in, not automatic cost-based selection — see next section.

## Does any system treat a secondary index as a special case of a parameterized materialized view (removing indexes as a separate concept)? Does any sit inside a transactional OLTP engine with views updated in the same serializable transaction?

### Takeaway
No source found describes a system that fully collapses "secondary index" into "parameterized materialized view" as a single user-facing concept with no separate index abstraction — the closest is Materialize's internal "arrangement" mechanism, but it still exposes `CREATE INDEX` and `CREATE MATERIALIZED VIEW` as distinct objects. No surveyed system is a transactional OLTP storage engine that updates all its derived views inside the same serializable transaction as the base write across the board; pg_ivm is the closest *partial* instance (immediate/same-transaction maintenance, but as a Postgres extension covering opted-in views, not a wholesale re-architecture that eliminates separate indexes).

### Cited Findings
- Materialize: "the mechanisms that maintain materialized views are called arrangements," and arrangements are also what back indexes — "Materialize builds and maintains indexes on both the input and output collections" using the same in-memory, incrementally-updated structure that materialized views use; a custom index can be created to use a smaller/different key than a view's natural key, purely to shrink memory footprint. Multi-way joins can use indexes/arrangements for "delta joins" at no extra storage cost. — [materialize.com/docs/overview/arrangements](https://materialize.com/docs/overview/arrangements) **[High — primary doc]**
- Despite the shared mechanism, Materialize's docs still describe indexes and materialized views with **different semantics**: an index "holds arranged data in memory" (ephemeral, cluster-local, must be rebuilt if the cluster restarts) while a materialized view "saves results" to **durable storage**. They are not presented to the user as one object type. — [materialize.com/docs/overview/arrangements](https://materialize.com/docs/overview/arrangements) **[High]**
- pg_ivm's "immediate maintenance" mode updates the materialized view **inside the same AFTER-trigger / same transaction** as the base table DML — this is the one documented case found of view maintenance running under the same transaction boundary as the write, inside a mainstream OLTP engine (Postgres). It is still a bolt-on extension (requires `create_immv()` instead of native `CREATE MATERIALIZED VIEW`), and it does not replace or subsume B-tree secondary indexes as a concept — pg_ivm views and ordinary Postgres indexes coexist as separate mechanisms. — [github.com/sraoss/pg_ivm](https://github.com/sraoss/pg_ivm)
- Noria's base tables have their own storage engine (RocksDB) and are the roots of its dataflow graph; indexed lookups are required for an operator to run in "partial state" mode at all — i.e., Noria's own description subordinates its index concept to the dataflow/materialization model (an index lookup capability gates whether partial materialization is possible), which is suggestive of a unification, but no source states this as an explicit design claim ("we removed indexes as a concept"). Noria itself sits **outside** a conventional transactional SQL engine — it *is* its own storage+dataflow system, not embedded inside e.g. Postgres's/MySQL's transaction manager, and ReadySet (its commercial descendant) explicitly sits **downstream of** an existing Postgres/MySQL instance via logical replication, i.e., views are maintained **asynchronously after** the upstream transaction commits, not inside the same serializable transaction. — [acolyer.org summary](https://blog.acolyer.org/2018/10/29/noria-dynamic-partially-stateful-data-flow-for-high-performance-web-applications/); [docs.readyset.io/concepts/overview](https://docs.readyset.io/concepts/overview) **[Medium]**
- Oracle/SQL Server indexed/materialized views are maintained either in the same transaction (`ON COMMIT`/immediate refresh options exist in Oracle) or deferred (`ON DEMAND`), but in all documented cases they remain a **distinct object type** from a B-tree secondary index, with their own restrictions (determinism, no outer joins in SQL Server, schemabinding) — these systems keep "index" and "materialized/indexed view" as two different features with different allowed query shapes, not one unified concept. — [sqlshack.com SQL Server indexed views](https://www.sqlshack.com/sql-server-indexed-views); [dbi-services.com Oracle refresh](https://www.dbi-services.com/blog/oracle-materialized-view-refresh-fast-or-complete/)

### Inferences
- The unification the user's candidate system proposes (index = parameterized IVM view, no separate index concept, inside the OLTP engine's own serializable transaction) appears to be a genuine combination not found as a single existing system in this search: prior art supplies the "shared incremental-dataflow mechanism" half (Materialize/DD, Noria) and, separately and partially, the "same-transaction/inside-the-engine" half (pg_ivm, Oracle/SQL Server's immediate-refresh/indexed views) — but no source combines full query-generality-as-the-only-access-path with in-engine serializable-transaction maintenance. **[Medium confidence on the absence claim — based on a reasonably thorough but time-boxed search, not an exhaustive literature review]**

### Gaps
- Did not find and could not fetch a working ReadySet "architecture" primary page (guessed URL 404'd); the official docs.readyset.io/concepts/overview page was only summarized via WebSearch snippet, not fetched in full, so ReadySet's precise handling of read-after-write / transactional consistency relative to the upstream database is not confirmed to primary-source depth.
- Did not find literature specifically evaluating whether Oracle's or SQL Server's *immediate*-refresh materialized/indexed views run within the exact same serializable transaction as the triggering DML (as opposed to a subsequent, same-session but separate internal transaction) — this distinction matters for the user's "same serializable transaction" criterion and was not resolved.

## Which systems choose automatically between "compute on read" and "maintain on write" by cost, and how?

### Takeaway
Noria is the clearest documented example of a per-query (really per-dataflow-path) choice between full materialization (pure maintain-on-write) and partial materialization with on-demand "upquery" reconstruction (a hybrid compute-on-read/maintain-on-write), gated by whether the read can be served by an index lookup — but this is a structural/feasibility gate, not an explicit cost-model optimizer choosing between the two strategies. No source found describes a system with an explicit, measured cost-based optimizer that decides per query whether to maintain a view incrementally versus compute it on read.

### Cited Findings
- Noria uses **partial state** for an operator "only when upqueries can be served by efficient index lookups" — if answering a cache-miss would require scanning an upstream operator's full state, Noria disables partial state for that operator and falls back to always-maintained (full) state instead. This is a binary, structural eligibility test applied per operator/query path, not a continuously-tuned cost model. — [acolyer.org summary of Noria OSDI'18](https://blog.acolyer.org/2018/10/29/noria-dynamic-partially-stateful-data-flow-for-high-performance-web-applications/)
- Within partial state, **eviction** (removing a cold entry, i.e., moving from "maintain" to "compute on next read") happens "under memory pressure," described as "like a cache," but the secondary source does not specify the eviction policy (LRU, LFU, etc.) or whether it is cost/frequency-aware. — [acolyer.org](https://blog.acolyer.org/2018/10/29/noria-dynamic-partially-stateful-data-flow-for-high-performance-web-applications/)
- ReadySet requires the operator to **manually** opt a query into caching via `CACHE QUERY '<select>'`; queries not explicitly cached are proxied straight through to the base database (pure compute-on-read via the upstream DB). This is documented as an explicit, operator-driven choice, not an automatic cost-based one. — [docs.readyset.io/concepts/overview via WebSearch summary](https://docs.readyset.io/concepts/overview)
- Materialize distinguishes unmaterialized views (compute-on-read, recomputed each query, no incremental maintenance) from indexed views and materialized views (maintain-on-write, incrementally updated); the choice between these is also made by the **user/DDL** (`CREATE VIEW` vs `CREATE INDEX ON ...` vs `CREATE MATERIALIZED VIEW`), not automatically by the system based on a cost estimate. — [materialize.com/docs/overview/arrangements](https://materialize.com/docs/overview/arrangements) **[High for the object-type distinction; inference that the choice is user-driven rather than cost-based]**
- Convex reruns a whole query function on a dependency change rather than compute-on-read vs. maintain-on-write per se; there is no evidence of a cost-based choice — it is uniformly "maintain by re-execution and diff," mediated only by which queries have active subscribers (no subscriber ⇒ effectively compute-on-read/pull in Convex's broader query model, though this split was not directly documented in the sources found). — [docs.convex.dev/realtime](https://docs.convex.dev/realtime) **[Low — this specific pull/push split for Convex was not directly confirmed by a fetched primary source]**

### Inferences
- "Automatic, per-query, cost-based choice between compute-on-read and maintain-on-write" — as a *general-purpose optimizer decision* comparable to how a query planner picks a join order — does not appear to exist in any surveyed system. The closest real analogue, Noria's partial-state gating, is a **feasibility** rule (can an index-lookup-based upquery serve this operator's misses?) combined with **LRU-like eviction under memory pressure**, not a cost-based optimizer weighing write amplification against read latency and choosing per query. **[Medium confidence on the absence — based on the sources read, not an exhaustive survey of all Noria/ReadySet internals, which were only accessible via secondary summaries]**

### Gaps
- Could not confirm Noria's exact eviction policy (LRU vs. something more sophisticated) from a primary source — only the acolyer.org secondary summary was accessible as text; the OSDI'18 PDF itself could not be read as text via the available fetch tool.
- No source found quantifies any system actually comparing estimated read frequency/cost against write-maintenance cost to decide incremental-maintenance eligibility automatically (e.g., "maintain this view only if its read:write ratio exceeds X") — if such a mechanism exists in Feldera, RisingWave, or ReadySet's newer releases, it was not surfaced by this search pass.

## What are the known limits (storage blow-up, write amplification, joins/aggregates with deletes, consistency, recursive queries)?

### Takeaway
Every mechanism studied pays for incremental maintenance with some combination of extra storage, write amplification on the base table, and either restricted query shapes (SQL Server) or substantially harder algorithms (outer joins, recursion, deletes) — DBSP/Feldera is the strongest claim found of removing the delete/update and recursion restrictions in principle (via Z-set retractions and stratified-Datalog fixed-point circuits), while SQL Server indexed views and classic trigger-based materialized views (e.g., Cassandra-family, ClickHouse) are the most restricted and the most quantified for write-amplification cost.

### Cited Findings
- **Storage blow-up**: Noria's partial state carries roughly **3× the base-table storage size** on the Lobsters benchmark. — [acolyer.org](https://blog.acolyer.org/2018/10/29/noria-dynamic-partially-stateful-data-flow-for-high-performance-web-applications/)
- **Storage blow-up (aggregation-driven)**: ClickHouse's own guidance warns that a materialized view with a high-cardinality `GROUP BY` can end up **larger than the raw source table** (a cited real case: a 20 GB raw log table produced a view roughly **10× larger**), because the view emits close to one row per distinct attribute combination rather than compressing; ClickHouse recommends checking the aggregation ratio before creating such a view (under 10% distinct-row-ratio is safe, over 70% risks "storage explosion"). — [ClickHouse docs: materialized views tips](https://clickhouse.com/docs/resources/support-center/tips-and-tricks/materialized-views)
- **Write amplification**: Altinity benchmarks (cited via a third-party guide) found that attaching **one** materialized view to a ClickHouse table at small (100-row) batch sizes cuts insert throughput by roughly **55%**, rising to about **80%** with five chained views and about **90%** with ten. DataStax (Cassandra-family) documentation states each materialized view adds roughly **10% write latency** on the base table, and also slows deletes on the source table. — [bigdataboutique.com ClickHouse guide](https://bigdataboutique.com/blog/clickhouse-materialized-views-guide); [DataStax materialized views concepts](https://docs.datastax.com/en/cql/hcd/develop/materialized-views-concepts.html) **[Medium — these numbers are from vendor/third-party benchmarks for specific trigger-based/replication-based MV implementations (ClickHouse, Cassandra-family), not from Noria/DBSP/Materialize, so they may not transfer directly to dataflow-based IVM engines]**
- **Joins and aggregates with deletes**: DBSP's Z-set model represents deletes/updates as **negative multiplicities**; because Z-sets form a group under addition, "negation gives deletion for free," and the incremental join operator is **bilinear** (`ΔR ⋈ S` and `R ⋈ ΔS` combine correctly), so deletes propagate correctly through joins and (per the paper) aggregates without special-casing. The paper does flag that **some operators need extra care with negative weights** — e.g., `DISTINCT` must explicitly "remove" elements that end up with negative multiplicity rather than naively treating them as present. — [arXiv 2203.16684 (DBSP paper)](https://arxiv.org/pdf/2203.16684); [Feldera blog: SQL on Z-sets](https://www.feldera.com/blog/SQL-on-Zsets/)
- **Joins and aggregates with deletes (classic limitation)**: SQL Server indexed views **disallow `OUTER JOIN` entirely**, specifically because "rows can logically disappear from an Indexed View based on `OUTER JOIN`" when a row is inserted into a base table — i.e., the classic incremental-maintenance algorithm used by SQL Server cannot correctly/efficiently handle outer-join deletions-by-insertion, so the feature is blocked outright rather than handled. Aggregate indexed views require `COUNT_BIG(*)` specifically so deletes/updates can be correctly incrementally counted. — [sqlauthority.com: Outer Join Not Allowed in Indexed Views](https://blog.sqlauthority.com/2010/09/24/sql-server-outer-join-not-allowed-in-indexed-views-limitation-of-the-view-8/); [sqlshack.com SQL Server indexed views](https://www.sqlshack.com/sql-server-indexed-views)
- **Consistency between base data and views**: Noria's documented guarantee is **eventual consistency** (views converge to match base-table state once writes quiesce), not linearizable/serializable read consistency with the base table. — [acolyer.org](https://blog.acolyer.org/2018/10/29/noria-dynamic-partially-stateful-data-flow-for-high-performance-web-applications/)
- **Consistency (the transactional counter-example)**: pg_ivm's "immediate maintenance" mode is the one documented mechanism giving **same-transaction** consistency between a base-table write and its materialized view, by running the view update in an `AFTER` trigger inside the writing transaction. — [github.com/sraoss/pg_ivm](https://github.com/sraoss/pg_ivm)
- **Recursive queries**: classic incremental view maintenance for recursive views/Datalog traditionally relies on **Delete-and-Rederive (DRed)**, described in the literature as "very inefficient" — it first deletes every derivation that touches a changed fact, then recomputes from scratch, and only afterward checks what actually changed. Some systems sidestep full generality by restricting to **linear recursion** (e.g., for transitive closure specifically) rather than solving the general recursive case. — [arXiv 2208.00273: Optimizing Differentially-Maintained Recursive Queries](https://arxiv.org/pdf/2208.00273); [arXiv 1804.10565: Certified Graph View Maintenance with Regular Datalog](https://arxiv.org/pdf/1804.10565)
- **Recursive queries (claimed advance)**: DBSP claims a general algorithm covering both monotonic and non-monotonic recursion by compiling stratified Datalog into a **fixed-point circuit**, explicitly contrasted with prior techniques "built for restricted classes" (plain relational algebra or Datalog) that the authors say don't generalize to richer languages. This claim comes from the DBSP authors themselves (VLDB 2023 Best Paper) and was not independently re-verified against a third-party benchmark or critique in this search. — [arXiv 2203.16684](https://arxiv.org/pdf/2203.16684) **[Medium — authors' own claim, not independently replicated/critiqued by a third party in the sources found]**
- A 2025 survey on **recursive-view maintenance** (Dong & Su, cited via Wright State repository) states the choice of maintenance language and the **minimal arity of auxiliary relations needed** for incremental recursive maintenance (e.g., transitive closure) remain **open research questions** — i.e., even post-DBSP, the recursive case is not treated in the literature as fully closed. — [Wright State repository: Incremental Maintenance of Recursive Views](https://corescholar.libraries.wright.edu/knoesis/410) **[Medium — citation found via search snippet, original publication date/venue not independently confirmed]**

### Inferences
- The field shows a consistent trade curve: the more general the incremental-maintenance algorithm (DBSP's Z-sets claim to handle arbitrary deletes/joins/aggregates/recursion uniformly), the more it is positioned as a standalone computational theory/engine (DBSP "is not a database") rather than as the native index/storage mechanism of a transactional engine; conversely, the systems embedded closest to the OLTP transaction (SQL Server indexed views, pg_ivm) impose the tightest query-shape restrictions (no outer joins, limited aggregate forms) precisely to keep the incremental-maintenance algorithm tractable within a transaction's time budget. **[Medium — synthesized across findings above, this specific trade-off framing is the researcher's own conclusion]**
- This trade-off is itself the most concrete "gap" the candidate system (part 2) would need to resolve: no prior-art source demonstrates a system that gets DBSP-level generality (arbitrary deletes, joins, aggregates, and recursion handled uniformly) while also running natively inside an OLTP engine's own serializable transaction as the sole index mechanism. **[Medium confidence on this specific absence, consistent with the absence claim made in the second section above]**

### Gaps
- No quantified, apples-to-apples benchmark was found comparing storage blow-up or write amplification specifically for **dataflow-based IVM engines** (Noria, Materialize/DD, DBSP/Feldera, RisingWave) against each other; the hard numbers found (ClickHouse, Cassandra/DataStax) come from trigger/replication-based materialized-view implementations in operational databases, which use a different maintenance mechanism and may not be representative of dataflow-based IVM's actual cost profile.
- Could not find a direct discussion in DBSP/Feldera's own materials of storage blow-up or write amplification bounds (the DBSP paper's focus found in this search was correctness/generality, not a cost/overhead analysis) — if Feldera has published benchmark numbers on memory/storage overhead vs. base data size, they were not surfaced in this search pass.
- Could not independently verify whether DBSP's claimed uniform handling of recursion is actually a solved problem in production use (e.g., in RisingWave or another DBSP-adjacent system) versus a theoretical capability demonstrated only in the paper's formalism — the Dong & Su citation suggests open questions remain in the broader literature, but it's unclear whether that survey predates or postdates (and thus accounts for) the DBSP result.
