# Migrations as compiled workload diffs, and combined "closed-world / workload-compiled database" systems

## Part 5 — closest prior art for migrations computed as a compiler diff between workload versions, backfilled from a log

### Takeaway
No system or paper found derives a migration from a **diff of the application's queries/transactions** (a workload diff). Every prior-art line — online DDL tools (gh-ost, pt-osc, F1, CockroachDB), declarative schema-diff tools (Atlas, Skeema, Bytebase), log/event-sourced systems (XTDB, Datomic, Noria), and academic schema-evolution tools (PRISM, InVerDa/BiDEL, Bullfrog, Tesseract) — computes the diff over the **schema** (DDL, table/column shape) and backfills data to match that diff. The "diff two compiled workload versions, derive the migration, backfill from the log" framing (part 5 of the candidate concept) is not matched by any source found; confidence is **medium-high** that this specific framing is absent from the literature searched (search budget limits an exhaustive claim to "no reliable source found" rather than "proven absent").

### Cited Findings
- **gh-ost** (GitHub): triggerless, asynchronous — tails the MySQL binlog to capture writes and applies them to a shadow table instead of using synchronous triggers; typically reads from a replica. — [Bytebase: gh-ost vs pt-online-schema-change](https://www.bytebase.com/blog/gh-ost-vs-pt-online-schema-change/)
- **pt-online-schema-change** (Percona): synchronous — INSERT/UPDATE/DELETE on the source table fire triggers that write to a "ghost" table in the same transaction; supports foreign keys via `--alter-foreign-keys-method`, which gh-ost does not support (foreign keys must be dropped/recreated). — [Bytebase](https://www.bytebase.com/blog/gh-ost-vs-pt-online-schema-change/)
- A 2017 Percona benchmark found gh-ost had negligible overhead in the copy stage versus a 12% performance drop for pt-osc (copy stage only, 2017 data). — [Percona benchmark](https://www.percona.com/blog/2017/07/12/gh-ost-benchmark-against-pt-online-schema-change-performance/)
- **F1 (Google, VLDB 2013), "Online, Asynchronous Schema Change in F1"**: the protocol is asynchronous (different servers can run on different schema versions at once) and online (all servers can read/write throughout). The paper shows many common schema changes can cause data **anomalies/corruption** under naive asynchronous rollout, and replaces them with a provably safe sequence of smaller schema changes, correct as long as no server is more than one schema version behind. — [Research paper, Google Research](https://research.google/pubs/online-asynchronous-schema-change-in-f1/); [PVLDB 6(11)](https://mail.vldb.org/pvldb/volumes/6/paper/Online%2C%20Asynchronous%20Schema%20Change%20in%20F1)
- **CockroachDB**: schema-change engine descends directly from the F1 approach — it rolls out a new schema while the old one is still in use via multiple concurrent schema **versions**, running the actual data backfill (or delete) as a background job that can be paused/resumed/canceled while the cluster keeps serving reads/writes. A new index is created delete-only → delete-and-write-only (backfill happens in this state, forwarding new writes too) → public, only after all nodes agree on the DW state. — [CockroachDB blog](https://www.cockroachlabs.com/blog/how-online-schema-changes-are-possible-in-cockroachdb/); [online primary key changes blog](https://www.cockroachlabs.com/blog/online-primary-key-changes/)
- **Atlas** (Ariga/HCL-based) and **Skeema** are both *declarative, schema-diff* tools: the operator declares the desired end-state schema (as HCL or SQL DDL) and the tool computes the DDL diff against the live schema; **Bytebase** adds a review workflow around the same diff-and-apply model. All three hand off the actual execution of large/live-table changes to an online DDL tool such as gh-ost or pt-osc rather than doing the backfill themselves. — [2026 migration-tools comparison](https://www.youngju.dev/transcribe/culture/2026-05-14-database-migration-tools-2026-atlas-bytebase-skeema-liquibase-flyway-pg-online-comparison-deep-dive); [Bytebase tool list](https://bytebase.com/blog/top-open-source-mysql-migration-tools)
- **PRISM / PRISM++ (Curino, Moon, Zaniolo/Deutsch; ICDE 2009 demo, VLDB Journal 2012/2013)**: schema evolution expressed as a small SQL-like language of **Schema Modification Operators (SMOs)**; the toolkit evaluates the SMOs' effect, auto-translates old queries/updates against the new schema, migrates the data, and documents the change. Validated on 170+ versions of Wikipedia's schema history and ~15 other evolution histories. This is schema-SMO-diff, not workload-diff — SMOs operate on table/column structure, and query rewriting is a *consequence* of the schema diff, not the driver of it. — [VLDB Journal, doi.org/10.1007/S00778-012-0302-X](https://www.doi.org/10.1007/S00778-012-0302-X); [ICDE 2009 PRISM Workbench demo](https://pubs.dbs.uni-leipzig.de/se/node/875)
- **InVerDa / BiDEL (Herrmann et al., TU Dresden, SIGMOD 2017)**: lets multiple schema **versions** of one relational database coexist; developers write short bidirectional Datalog-based BiDEL scripts describing a schema delta, and the system generates the views/triggers that keep every coexisting version in sync (writes through any version propagate to all others). DBAs can also change physical layout without taking any version offline. Authors report BiDEL scripts are much shorter/more robust than hand-written migration SQL, with modest performance overhead. Still schema-version-diff, explicitly bidirectional between two *schemas*, not a diff of query workloads. — [arXiv:1608.05564](https://arxiv.org/pdf/1608.05564)
- **Bullfrog (SIGMOD 2021), "Online schema evolution via lazy evaluation"** and **Tesseract (VLDB 2023/arXiv 2210.03958), "Online Schema Evolution is (Almost) Free for Snapshot Databases"**: both deliver online, transactional, near-zero-overhead schema changes under snapshot isolation; found only via secondary citation/abstract, not read in full. — [arXiv:2210.03958](https://arxiv.org/pdf/2210.03958)
- **XTDB**: an immutable, append-only-log database that enforces **no schema**; a documented pattern for "migration" is to write a program that walks each entity's history and backfills a new derived field going forward, and a community warning that rewriting old entities loses history — the recommended approach is to re-apply the "migration" as new transactions on top of the log (keeping full history) rather than true in-place rewriting. This is a log replay/backfill mechanism, but it is schema-less, so there is no schema (or workload) diff driving it — it is a hand-written, ad hoc migration script. — [Biff: XTDB compared to other databases](https://biffweb.com/p/xtdb-compared-to-other-databases/); [Clojurians log, xtdb channel 2022-04-27](https://clojurians-log.clojureverse.org/xtdb/2022-04-27)
- **Datomic**: a 2016 community thread describes a third-party library that runs a named, ordered set of migration transactions once each and tracks which have already run (a Rails-style migration runner over a log), with schema attribute changes (e.g., adding full-text search to an attribute) named as the main pain point. No workload-diff mechanism found. — [Clojurians log, Datomic channel 2016-01-11](https://clojurians-log.clojureverse.org/datomic/2016-01-11)
- **Noria** (MIT PDOS research dataflow database, predecessor to ReadySet): developers declare queries, not a fixed schema; Noria "provides fast schema migrations" because migrations **reuse existing materialized dataflow state**, and because the raw write log is retained, a migration can be rolled back and old queries can still be answered afterward. This is the one system found where "migration" is explicitly tied to the query/dataflow graph rather than to a table schema — but no further detail was retrievable on how a migration is *computed* (i.e., whether it is a diff of two compiled query sets) versus manually specified by the developer adding a new query. — [Noria project overview, MIT PDOS](https://vm-web.pdos.csail.mit.edu/projects/noria.html)
- No source was found describing ReadySet's (Noria's commercial successor) current migration mechanism — the search returned only Noria-era research material.

### Inferences
- The field cleanly splits into two unconnected camps: (a) **schema-diff** tools (gh-ost/pt-osc/F1/CockroachDB/Atlas/Skeema/Bytebase/PRISM/InVerDa/Bullfrog/Tesseract) that diff table/column DDL and then backfill or dual-write data to match, and (b) **schema-less log-replay** systems (XTDB, Datomic) that treat "migration" as an ad hoc backfill script over history, with no compiled diff at all. Noria is the only system found whose migration story is query/dataflow-centric rather than DDL-centric, but it is description-level only ("fast migrations because views are reused"), not a documented algorithm that diffs two compiled workloads.
- No source frames migration as "recompile the workload, diff the two compiled plans/index sets, and the delta tells you exactly what must be backfilled" — the candidate concept's part 5 appears to be a genuine combination not published elsewhere, built from parts that each exist in isolation (schema-diff tooling + log backfill + per-query incremental materialization).

### Gaps
- Declarative tools in the key-questions list that were **not independently sourced**: Prisma Migrate (a direct search was not run after the generic migration-tools search did not surface it) — do not treat any claim about Prisma Migrate's diffing mechanism as sourced here.
- No primary source was retrieved for ReadySet's (vs. Noria's) migration mechanics, or for Rama's (Red Planet Labs) schema/migration model — a case study confirmed a team moved Datomic→XTDB→Rama but gave no mechanism detail. — [Red Planet Labs case study](https://blog.redplanetlabs.com/2025/03/04/how-multiply-went-from-datomic-to-xtdb-to-rama/)
- Kafka-based "rebuild views from the log" patterns (ksqlDB, Kafka Streams materialized views) and Datomic's own official migration guidance were not directly searched; general-purpose "replay the event log to rebuild a view under a new schema" is a known pattern in event-sourcing but no primary citation was retrieved in this pass.

## Part — combination search: does any system combine closed-world compilation, IVM, deterministic scheduling, and invariant-driven coordination?

### Takeaway
No system or paper found combines more than two of the six listed parts. The closest single-axis matches are: **Bespoke OLAP / JetStream (2026)** for compile-time workload specialization of storage+execution (but OLAP-only, no transactions/invariants/migration); **Noria** for workload-compiled incremental views + migration-via-materialized-state-reuse (but no deterministic parallel scheduling or invariant-based coordination, and it's a discontinued research project); **VoltDB** for deterministic, statically-analyzed, partitioned transaction scheduling (but no IVM of arbitrary queries as the storage model, and indexes are developer-declared, not workload-derived); **Zero (Rocicorp)** and **Feldera (DBSP)** for IVM as the core execution model (but no transactional invariants or migration story); **TigerBeetle** for invariant-density-as-correctness-strategy (but it is a fixed-schema ledger, not a compiled arbitrary workload). Confidence is **medium** that no closer combination exists in a search of this depth — a deeper literature pass (full VLDB/SIGMOD/CIDR proceedings crawl) could not be completed in the available budget.

### Cited Findings
- **Convex**: reactive database where queries are TypeScript functions that re-run automatically when their dependency data changes, with client subscriptions updated incrementally; ACID with serializable isolation via **optimistic concurrency control** (not static read/write-set scheduling); the hosted product persists on PlanetScale/MySQL, the OSS version supports SQLite/Postgres/MySQL. No sourced detail on compile-time workload analysis, workload-derived indexes, or a migration-as-workload-diff mechanism — Convex's own docs describe developer-declared indexes (`.withIndex()`), not workload-derived ones. — [Convex docs: Understanding Convex](https://docs.convex.dev/understanding/overview)
- **SpacetimeDB**: application logic ("modules") compiles to WebAssembly and runs inside the database; the model has three function kinds — **reducers** (transactional writes), **procedures** (external calls), and **views** (read-only computed queries); the FAQ states subscriptions are evaluated and pushed incrementally when underlying data changes; all data held in memory, persisted via a replayable commit log. Development-commit-log evidence (not official docs, lower confidence) suggests the query engine always assumes a view is backed by a materialized table, implying IVM-like treatment of views. No sourced evidence of workload-derived physical layout, static read/write-set scheduling, or a migration-by-workload-diff mechanism. — [SpacetimeDB docs: databases](https://spacetimedb.com/docs/databases); [SpacetimeDB FAQ](https://spacetimedb.com/docs/intro/faq)
- **Feldera (DBSP)**: VLDB 2023 Best Paper; a general incremental-computation framework (not SQL-specific) representing data and deltas uniformly as **Z-sets** (signed multisets) so insertions and deletions are handled by the same operators; supports full relational queries, aggregation, recursion, and streaming aggregation; SQL views are compiled to Rust via a SQL-to-DBSP compiler. No sourced evidence on determinism guarantees, transactional invariants, or schema migration as workload diff — these were explicitly not found despite a targeted search. — [DBSP paper](https://ar5iv.labs.arxiv.org/html/2203.16684); [Feldera VLDB 2023 best paper announcement](https://feldera.com/blog/Best-Research-Paper-VLDB-2023)
- **VoltDB**: requires stored procedures to be **deterministic** so the same procedure run on redundant partition copies produces identical results; documented non-determinism sources are system-specific functions/I/O, misused static variables, and mutating parameters; unsorted SQL results are a common nondeterminism trap unless an index-ordered scan or explicit ORDER BY is used. Procedures are statically partitioned. No sourced detail on whether partitioning/indexes are workload-*derived* at compile time (VoltDB's model is developer-declared partition keys) or on IVM of declared queries. — [VoltDB docs, "Designing Stored Procedures"](https://docs.voltactivedata.com/UsingVoltDB/DesignProc.php)
- **DBOS** (VLDB 2022 paper "DBOS: A DBMS-oriented Operating System", Stonebraker/Zaharia/Kraska et al., Stanford/MIT): proposes running OS services (scheduling, file management, IPC) as queries/transactions on top of a distributed transactional DBMS rather than a conventional kernel, arguing this lets low-latency-transaction and HA logic be implemented once in the DB layer instead of duplicated per OS component; reports performance competitive with existing OS mechanisms. This is an architectural argument for "database as the one source of truth for all state," conceptually adjacent to "closed-world" but is about OS design, not about compiling an application's query/transaction workload into a specialized engine with workload-derived layout or IVM. Commercial DBOS Cloud claims (serverless TypeScript platform) are company claims, not independently verified. — [DBOS VLDB paper](https://web.stanford.edu/~kozyraki/publication/2021-dbos-vldb); [PVLDB 15(1)](https://mail.vldb.org/pvldb/volumes/15/paper/DBOS%3A%20A%20DBMS-oriented%20Operating%20System)
- **TigerBeetle**: a fixed-domain (financial ledger) OLTP database; design philosophy ("TigerStyle") mandates an average of ≥2 assertions per function covering pre/postconditions and invariants, a hard 70-line function cap, fixed upper bounds on every loop/queue/buffer, no multithreading, and static (not dynamic) memory allocation; its creator states the system must be correct "across literally thousands of invariants." This is invariant-density-as-engineering-discipline for a *fixed* schema/workload (the ledger primitive), not compile-time specialization of an arbitrary application's workload, and not IVM or migration-by-diff. — [TigerStyle summary](https://notes.billmill.org/programming/programming_essays/TIGER_STYLE.html); [Zig asserts discussion](https://kristoff.it/blog/fix-your-asserts/)
- **Riffle (Ink & Switch / MIT CSAIL, UIST 2023)**: a client-side reactive relational-state system for local-first apps — holds the whole app state in a client-side SQLite-backed relational database, with queries forming a reactive dependency graph maintained incrementally (spreadsheet-like). Prototype used SQLite + React via WASM. Authors report the reactive-relational model aided debuggability/responsiveness but also surfaced friction with existing tooling. This is IVM for client-side app state, not a backend database with workload-derived physical design, deterministic scheduling, or invariant-based transaction coordination. — [Riffle UIST'23 paper](https://groups-csail-mit-edu.ezproxy.canberra.edu.au/sdg/pubs/2023/riffle-uist-23.pdf); [MIT DSpace record](https://dspace.mit.edu/handle/1721.1/152980)
- A related 2023 master's thesis built **incrementally maintained materialized views on SynQLite**, a CRDT-based SQLite extension, finding incremental refresh generally faster than full refresh at the cost of extra storage — another isolated IVM data point, not a combined system. — [UiT Munin thesis record](https://munin.uit.no/handle/10037/30400)
- **Zero (Rocicorp)**: reached general-availability "1.0" in 2026; server-side sync engine (`zero-cache`) keeps a SQLite replica of Postgres; its query language **ZQL** is explicitly described as "an Incremental View Maintenance (IVM) query engine," running on both client and server, pushing only diffs to clients; a query-plan analyzer tool (`analyze-query`) is provided to catch unoptimized plans (e.g., `TEMP B-TREE`). No sourced detail on compile-time workload-derived indexes, static read/write-set scheduling, invariants, or schema migration as workload-diff — Zero's underlying schema is the replicated Postgres schema, migrated by ordinary Postgres means. — [Zero docs](https://zero.rocicorp.dev/docs); [InfoQ: Zero reaches v1.0 (2026)](https://infoq.com/news/2026/06/zero-version-1)
- **ElectricSQL** and **Instant(DB)** were found only as named alongside Zero/Convex/PowerSync in comparison lists; no sourced architectural detail on either was retrieved in this pass. — [thenewstack.io: sync engines overview](https://thenewstack.io/how-a-new-breed-of-sync-engines-solves-frontend-problems/)
- **Bespoke OLAP (Wehrstein, Eckmann, Jasny, Binnig; TU Darmstadt; PVLDB vol. 19, 2026)**: synthesizes a "one-size-fits-one" OLAP engine for a single fixed workload, covering storage through query execution, using an LLM-driven synthesis pipeline with iterative performance evaluation and automated validation (plain LLM prompting alone does not yield a correct/efficient engine); claims order-of-magnitude speedups over general-purpose engines (e.g., DuckDB) for workloads matching enterprise data warehouses' stable, parameterized query-template suites; generation takes minutes to hours. This is the closest match found to "compile the complete known workload into a specialized engine," but the abstract makes **no mention** of incremental view maintenance, transactions, invariants, deterministic scheduling, or migration — it is a batch OLAP engine generator, not an OLTP/live system, and gives no account of what happens when the workload changes (no migration-as-diff mechanism described). — [arXiv:2603.02001](https://arxiv.org/abs/2603.02001v1); [Bespoke OLAP VLDB talk listing](https://hpi.de/en/database-group/teaching/summer-term-2026/advanced-error-detection-1/johannes-timo/)
- **JetStream (arXiv:2608.22476, 2026)**: explicitly positions itself against Bespoke OLAP and "GenDB," criticizing them for rewriting the base data representation itself (which it says complicates writes); JetStream instead generates query **accelerators** layered on top of an existing, unmodified DBMS, aiming to support ad-hoc queries (not just the fixed known workload) while preserving acceleration under writes. This is a direct rebuttal of the "closed-world, workload-is-fixed" premise from inside the same research thread. — [arXiv:2608.22476](https://arxiv.org/pdf/2608.22476)
- **FaunaDB**: ceased operations as a managed service on 30 May 2025 for funding/market reasons (not technical); the team stated an intent to open-source the core engine, drivers, and FQL query language. No sourced architectural link to closed-world compilation was found — FaunaDB is a general-purpose document-relational serverless database, not a workload-compiled one. — [The Register, 24 Mar 2025](https://www.theregister.com/2025/03/24/faunadb_shut_down/); [InfoQ](https://infoq.com/news/2025/03/fauna-shuts-down)
- **Turso/Limbo**: no evidence found connecting it to any of the six parts; it is understood (not independently re-verified in this pass beyond general knowledge) as a Rust rewrite of SQLite aimed at embedded/edge deployment, not a workload-compiled closed-world engine. Flagged as a gap rather than a sourced negative.

### Inferences
- The six parts cluster into two research lineages that have not yet been merged: an **OLAP/analytics lineage** (Bespoke OLAP, JetStream, and by extension classic "database cracking"/self-tuning-index research not directly re-sourced here) working on compile-time, workload-derived physical specialization, and an **OLTP/reactive-app lineage** (Convex, Zero, SpacetimeDB, Noria, Riffle) working on IVM-backed reactive queries and transactions, generally with developer-declared (not workload-derived) indexes and OCC or application-level consistency rather than static read/write-set scheduling or declared invariants replacing isolation levels.
- Deterministic, statically-scheduled transaction execution (part 3) is attested only in VoltDB/Calvin-style systems, which were designed before the IVM-as-storage-model and LLM-driven workload-compilation trends (Feldera 2023, Bespoke OLAP/JetStream 2026) and have not been reported as merged with them.
- "Invariants instead of isolation levels" (part 4) as a named, systematized coordination mechanism was not found anywhere; TigerBeetle's invariant-dense style is the closest cultural analog but is applied as a defensive-coding discipline on a fixed schema, not as the actual concurrency-control mechanism replacing isolation levels.
- Taken together, the candidate concept's combination of all six parts was not found published or shipped anywhere in the sources reached; the strongest individual precedents per part are: (1) Bespoke OLAP/JetStream; (2) Zero/Feldera/Noria/Convex; (3) VoltDB; (4) none found, TigerBeetle as a weak analog; (5) see Part 5 findings above (no match found); (6) not directly sourced in this pass (see Gaps).

### Gaps
- Part 6 ("compile-time cost bounds per operation") was not directly searched as its own question; no source was retrieved either confirming or denying any system offers statically-derived per-operation cost bounds (as opposed to runtime cost estimation/EXPLAIN-style estimates). This should be treated as an open gap, not a negative finding.
- XTDB **v2** specifically (as opposed to XTDB generally) was not distinguished in search results; claims above about XTDB's log/migration model may not reflect v2-specific changes.
- Electric(SQL) and Instant(DB) architecture (query compilation, IVM mechanics) were not independently sourced — only named in a third-party comparison list.
- A full crawl of CIDR/VLDB/SIGMOD 2023–2026 proceedings for "workload compilation," "closed-world database," or "invariant-driven concurrency control" as exact research threads was not completed within the tool budget; a deeper pass (dblp + ACM DL + arXiv listing crawl) is recommended before asserting absence with high confidence.

## Literature on closed-world database design (for/against) and the Stonebraker & Pavlo 2024 survey

### Takeaway
"Closed-world" has an established, unrelated meaning in database theory — the **closed-world assumption (CWA)** about missing facts being false (Reiter 1977/1978 line of work) — and no source was found using "closed-world" to mean "all application queries known at build time." The Stonebraker & Pavlo 2024 SIGMOD Record article ("What Goes Around Comes Around... And Around...") was located bibliographically but its full text could not be fetched in this pass, so its specific stance on workload-specialized/compiled engines is a **gap**, not a sourced finding.

### Cited Findings
- **Stonebraker & Pavlo, "What Goes Around Comes Around... And Around..."**, ACM SIGMOD Record 53(2):21–37, 2024 — confirmed bibliographic record as the successor to Stonebraker & Hellerstein's 2005 "What Goes Around Comes Around," covering roughly the next 20 years of data-model/query-language history. — [SIGMOD Record article page](https://sigmodrecord.org/2024/06/30/what-goes-around-comes-around-and-around); citation confirmed via [UBC course reading list](https://www.cs.ubc.ca/~rap/teaching/504/2025W2/topics/goesaround.shtml)
- The SIGMOD Record landing page for the article contains only title/authors/PDF-link/navigation; full text was not retrievable via web fetch in this pass, so **no claim about its content on workload-specialized engines, closed-world compilation, NoDB, or self-adaptive databases can be sourced** — none of those terms were present on the fetched page, but that is because the page has no body text, not because the paper omits them.
- **Closed-world assumption (CWA), classical sense**: a missing fact is treated as false. Reiter's 1977/1978 line of work (UBC TR-77-16) and later surveys discuss evaluating queries under CWA vs. open-world assumption; Motro (VLDB 1986) proposes "completeness information" metadata marking which database subsets satisfy CWA; Denecker et al. (KU Leuven) propose "locally closed" databases where a relation is complete only within a declared "window of expertise"; Razniewski & Nutt describe a "partial closed-world assumption" mixing closed and open parts. — [UBC TR-77-16](https://www.cs.ubc.ca/sites/default/files/tr/1977/TR-77-16.pdf); [KU Leuven, locally closed databases](https://lirias.kuleuven.be/retrieve/112410)
- None of these CWA-literature sources address the *workload-known-at-build-time* sense of "closed world" relevant to this research question — they are about incomplete *data*, not about a fixed, fully enumerated *query/transaction set*.

### Inferences
- The absence of any paper found using "closed-world" in the workload-compilation sense suggests the candidate concept's framing is either genuinely novel terminology, or exists under different vocabulary not yet searched (candidates not yet tried: "workload-specific database," "application-specific DBMS," "query-compiled database," "schema-on-write vs. schema-on-read," "vertical database," "narrow waist" — none of these alternate-vocabulary searches were run in this pass).
- Given that Bespoke OLAP/JetStream (found under "workload-aware" search terms, not "closed-world") are the closest technical precedent and are both from 2026, the "closed-world compiled database" framing as a named architectural pattern appears to be either very recent/unpublished or simply not yet indexed under that phrase.

### Gaps
- The actual argument of Stonebraker & Pavlo 2024 could not be retrieved (page had no body text); a direct PDF fetch (the SIGMOD Record page links to a PDF download, and the paper is also likely on Pavlo's CMU publications page or a preprint server) should be attempted separately to answer whether it argues for or against workload-fixed/compiled architectures, data independence, or "one size fits all."
- No classic "data independence critique" literature (e.g., arguments that physical/logical data independence is a liability once the workload is fully known, or the reverse argument that fixing the workload sacrifices future flexibility) was found under the search terms tried; this axis of the key question remains open.
- Self-adaptive/NoDB literature (e.g., Idreos et al.'s NoDB, adaptive indexing/database cracking) was not searched in this pass despite being named in the fetch prompt as a check — a dedicated search for "NoDB adaptive database Idreos" and "database cracking adaptive indexing" would close this gap.
