# Workload-Derived Physical Database Design and Compile-Time Cost Bounds

## Part 1 — What do existing self-designing/compiled-engine systems do, and where do they stop short of a whole engine compiled from a closed workload?

### Takeaway
Across data-structure synthesis (Data Calculator/Cosine/Limousine), whole-engine query compilers (LegoBase/DBLAB, HyPer/Umbra), and natively-compiled transaction systems (Hekaton, VoltDB), every system either (a) synthesizes/selects a *single* data structure or storage engine configuration from a workload description but still runs an interpreter or generic executor on top, or (b) compiles *queries/procedures* to native code but takes the physical schema, indexes and partitioning as externally given, rather than deriving the full index/layout/partitioning set *and* the query-execution code from one closed, build-time-known workload in a single compilation step. The one system found that attempts exactly that whole-engine-from-closed-workload compilation is "Bespoke OLAP" (2026), which uses an LLM agent rather than a formal synthesis or verified-compilation approach.

### Cited Findings
- **Data Calculator (Idreos et al., SIGMOD 2018):** a design engine with fine-grained "design primitives" capturing first principles of data layout; uses learned cost models (trained across hardware/data profiles) to *predict* the cost of a candidate data structure without implementing it, and can auto-complete partial designs or flag suboptimal ones — but it is a design-space exploration/what-if tool for a human or outer search loop, not a compiler that emits a running specialized engine — [The Data Calculator](https://stratos.seas.harvard.edu/publications/data-calculator-data-structure-design-and-cost-synthesis-first-principles-and); [arXiv/ar5iv version](https://ar5iv.labs.arxiv.org/html/1808.02066).
- **Design Continuums (Idreos et al., CIDR 2019):** unifies B+-tree, Bε-tree, LSM-tree and LSH-table under one parametrized model so a system can "learn" which point in the continuum fits a workload/memory budget — still single-structure key-value design, not a whole query engine — [CIDR 2019 paper](https://mail.vldb.org/cidrdb/papers/2019/p143-idreos-cidr19.pdf).
- **Cosine (Idreos et al., VLDB 2022, per Harvard bio) and Limousine (Chatterjee, Pekala, Kruglyak, Idreos, SIGMOD 2024):** self-designing key-value storage engines that adapt architecture to workload, cloud budget and performance target, combining learned and classical structures; Limousine generates Rust code and is reported (per an automated secondary summary, not independently verified in the paper itself) to beat RocksDB/WiredTiger/FASTER/Cosine on YCSB by up to 1000x — scope is a key-value store (get/put/scan), not a relational query/transaction engine with joins, indexes-for-queries, or partitioning across nodes — [DBScholar summary](https://rmarcus.info/dbscholar/papers/h84fc705745c9d182); [Harvard DASLab](https://datascience.harvard.edu/directory/stratos-idreos).
- **LegoBase/DBLAB (Klonatos, Koch, Rompf, Chafi, VLDB 2014):** a query engine written in a high-level language (Scala) that is source-to-source compiled ("generative programming") down to specialized low-level C per query; reported to outperform a commercial in-memory DB and an existing query compiler on TPC-H with only a few hundred lines of optimization code — but it compiles the *query execution* layer only; physical layout, indexes and partitioning are not derived by the system from the workload — [VLDB 2014 paper](https://arxiv.org/pdf/1612.05566); [EPFL record](https://infoscience.epfl.ch/record/223725?ln=en).
- **HyPer → Umbra query compilation (Neumann et al.; "Tidy Tuples and Flying Start," VLDB Journal 2020):** HyPer pioneered compiling whole SQL queries to native code; Umbra adds a custom IR (similar to LLVM IR) with two backends — a fast single-pass x86 backend ("Flying Start") for short queries and an LLVM -O3 backend for long-running queries — cutting compilation latency while keeping generated-code speed; on small data Umbra is reported faster than interpreters (DuckDB, PostgreSQL), on large data on par with HyPer — [Tidy Tuples and Flying Start](https://db.cit.tum.de/people/sites/kersten/Tidy%20Tuples%20and%20Flying%20Start%20Fast%20Compilation%20and%20Fast%20Execution%20of%20Relational%20Queries%20in%20Umbra.pdf); VLDB 2021 "production" paper on bringing the compiling engine to production, covering data-centric codegen and morsel-driven execution integration — [p3207 Neumann, VLDB 2021](https://www.vldb.org/pvldb/vol14/p3207-neumann.pdf).
  - Gap for Part 1: HyPer/Umbra compile the *query plan* given a *fixed, hand/optimizer-chosen* physical schema (tables, indexes) at execution time per query; they do not compile the schema/index/partitioning layer itself from a known workload at build time, and they still accept arbitrary ad-hoc SQL at runtime (open-world queries), not a closed, enumerated query set.
- **Hekaton (Microsoft SQL Server in-memory OLTP, VLDB 2013; summarized via multiple secondary sources):** compiles T-SQL stored procedures directly to native machine code at *procedure-definition* time, bypassing the interpreter; compiled procedures may touch only memory-optimized tables, with interop needed for mixed access to disk-based tables — [paper copy](https://web.eecs.umich.edu/~mozafari/fall2015/eecs584/papers/hekaton.pdf); [dbdb.io summary](https://dbdb.io/db/hekaton). Gap: compiles the *procedure body*, not the data structures/indexes (those are still chosen by a DBA/optimizer, with a constrained set of index types for the memory-optimized engine), and it does not compile a closed enumerated workload as a whole engine — new ad-hoc or uncompiled T-SQL is still supported via the interpreted path.
- **VoltDB stored procedures:** every stored procedure is precompiled; single-partition procedures run serialized on their partition's process without locking/latching/logs, giving low latency, while multi-partition procedures go through a coordinator and are slower; procedures must be deterministic (checked by hashing/comparing resulting SQL across replicas) — [VoltDB docs](https://docs.voltdb.com/UsingVoltDB/IntroHowVoltDBWorks.php); [Jepsen VoltDB 6.3 analysis](https://jepsen.io/analyses/voltdb-6-3); [dbdb.io](https://dbdb.io/db/voltdb). Gap: VoltDB's *partitioning* is chosen by the application developer (partition key per table) at schema-design time, not automatically derived by compiling the full known stored-procedure workload; Horticulture (below) is the automatic-partitioning add-on for this same H-Store/VoltDB lineage, run as a separate design-time tool, not integrated into one engine-compilation step.
- **Horticulture (H-Store's automatic partitioning design tool):** generates a partitioning strategy from schema, stored procedures, and a *sample* workload, using large-neighborhood search over a cost model comparing single-partition vs. distributed transaction cost — [H-Store partitioning paper](https://hstore.cs.brown.edu/papers/hstore-partitioning.pdf); [H-Store docs](https://hstore.cs.brown.edu/documentation/deployment/automatic-database-designer/). This is the closest classical system to "derive partitioning from a closed, known workload," but it only produces a partitioning *plan* fed into H-Store/VoltDB's existing engine — it does not also compile indexes, storage layout, or the query/transaction execution code; and it uses a *sample*, not a provably-complete/closed query+transaction set with any formal guarantee of optimality or coverage.
- **Schism (Curino, Zhang, Jones, Madden, VLDB 2010):** workload-aware graph partitioning/replication for shared-nothing OLTP, building a tuple co-access graph and cutting it, then using ML to turn the tuple placement into range predicates; tested on TPC-C, TPC-E, Epinions; reported up to 30% cut in distributed-transaction cost (per a secondary summary) — [Schism paper](https://cs.brown.edu/courses/csci2270/archives/2012/papers/partitioning/schism-vldb2010.pdf). Same gap as Horticulture: partitioning only, workload is a *sample*, not a closed/exhaustive set, and no compile-time cost guarantee is given.
- **Castor (Feser, Madden, Tang, Solar-Lezama; arXiv 2019 / OOPSLA-era venue unconfirmed in the fetched copy):** the closest prior art found for "compile indexes/layout from a known workload into a whole specialized engine" for *read-only* data. See full detail under Part 6 below (it is directly relevant to both parts); in short, Castor is a DSL + deductive-synthesis compiler that takes one fixed, parameterized query plus a static (slowly/never changing) dataset and synthesizes a specialized physical data layout and access code together, beating or matching HyPer on 15/18 TPC-H queries at 1GB scale with much lower memory — [arXiv 1903.03229](https://ar5iv.labs.arxiv.org/html/1903.03229).
- **Bespoke OLAP (Wehrstein, Eckmann, Jasny, Binnig; TU Darmstadt/DFKI/hessian.AI; arXiv 2603.02001, posted March 2026, PVLDB vol. 19):** an LLM-agent pipeline that takes a "DBMS contract" (schema, query *templates* with parameter ranges, and a sample Parquet dataset) and synthesizes a workload-specific OLAP engine from scratch — choosing storage layouts (sort orders, encodings, auxiliary structures), hash indexes, and sorted range directories, not just generating query code — validated by empirical benchmarking plus fuzz/differential testing against DuckDB, with automatic rollback on regression; reports order-of-magnitude speedups over DuckDB and Umbra, built in minutes to hours for roughly $121–125 in LLM API cost — [arXiv HTML](https://arxiv.org/html/2603.02001v1); [PVLDB vol.19 PDF](https://www.vldb.org/pvldb/vol19/p3759-wehrstein.pdf); companion piece "The Future Is Bespoke," IEEE Data Engineering Bulletin 2026 (same group).
  - Bespoke OLAP is the closest known system to "compile a whole engine from a closed workload" for Part 1's layout/index/co-location scope. It explicitly supports only the templated query set in its contract (anything else falls back to a general engine), is single-threaded and in-memory only (multi-threading and disk-resident data are explicit future work), and does not address OLTP/transactions/concurrency at all (explicitly future work). It gives **no formal or compile-time cost bound** — it "sidesteps cost modeling entirely" and instead empirically benchmarks candidate implementations, hard-coding whichever is fastest on sampled parameter instantiations.

### Inferences
- There is a clear two-decade trajectory — Data Calculator/Cosine/Limousine (single data structure, workload-informed) → LegoBase/HyPer/Umbra (whole-query compilation, schema/index given) → Hekaton/VoltDB (whole-procedure compilation, partitioning/schema given) → Castor (whole read-only query+layout co-synthesis, single query at a time) → Bespoke OLAP (whole read-only engine synthesis, templated multi-query workload) — each step closing part of the gap toward "compile the whole engine from the closed workload," but none closes all of it simultaneously (full relational feature set + writes/transactions + automatic partitioning across nodes + proven correctness + formal cost bounds) in one system.
- The automatic physical-design tuners (AutoAdmin and successors, see Part 2 notes if produced separately) and the Horticulture/Schism/Clay/E-Store partitioners are the deployed, production-grade analogue of "derive layout from workload," but they operate as *advisors* bolted onto a pre-existing general engine, consuming a *sample* workload rather than a provably closed/exhaustive one, and never touch query-execution code generation.
- No system in this search combines (i) a provably closed/complete workload specification, (ii) automatic derivation of indexes + data layout + partitioning together, and (iii) compilation of the whole query/transaction execution engine, in one step with a formal (non-empirical) guarantee. Confidence: **medium** — based on a broad but not exhaustive search; a system with this exact combination may exist in venues not surfaced (e.g., under a different name, or in systems/PL venues rather than DB venues).

### Gaps
- Could not confirm Castor's exact publication venue (OOPSLA vs. a SIGPLAN placeholder venue in the fetched text) or final published year — the fetched arXiv/ar5iv copy carried only an unfilled SIGPLAN template header; a separate OOPSLA 2020-dated paper "Deductive Optimization of Relational Data Storage" by *different* authors (Feser/Madden/Tang/Solar-Lezama, OOPSLA 2020, PACMPL vol. 4 art. 170) was also found in search snippets and may be the same work under its final venue — this should be disambiguated/verified directly from the ACM DL record before citing a venue.
- Did not find a system that automatically derives *cross-node partitioning* as part of the same compilation step that also derives indexes/layout and compiles query execution code (i.e., Bespoke OLAP and Castor are both single-node/in-memory).
- Did not verify the Limousine "up to 1000x" figure against the primary SIGMOD 2024 paper itself (it came from a secondary/automated summary only).

## Part 6 — Compile-time cost bounds per operation: does any system/paper give static worst-case cost guarantees, reject unbounded queries at build time, or co-design storage layout from application code?

### Takeaway
No system or paper found gives a true static/compile-time *worst-case cost bound* per database operation in the sense of "this query is guaranteed O(f(n)) at build time, or it is rejected." The closest pieces are: (a) program-analysis/synthesis systems that co-design storage layout from application/query code (Castor; Cheung et al.'s Query-by-Synthesis/StatusQuo line), which optimize but do not bound cost; (b) a large, mature body of *general-purpose* static resource-bound analysis (automatic amortized resource analysis, AARA) that proves worst-case cost bounds for functional/imperative programs, but which this search found **no** direct application of to database query engines or query languages; and (c) practical, heuristic, non-formal cost-threshold admission control (Greenplum's statement_cost limit; a 2025 patent on screening queries by worst-case predicate selectivity) that rejects expensive queries using the *cost estimator's* number, not a proven bound.

### Cited Findings
- **Castor (Feser, Madden, Tang, Solar-Lezama):** the compiler's internal search is cost-guided (it has a cost model it optimizes against), but that cost model estimates only query *runtime*, not layout size, and the paper documents the consequence directly: the optimizer "can produce layouts too large to be compiled efficiently" — i.e., there is no bound enforced, only a heuristic cost estimate used for search, and failure modes are observed empirically, not precluded by a proof — [arXiv 1903.03229 / ar5iv](https://ar5iv.labs.arxiv.org/html/1903.03229). Castor's synthesis is semantics-preserving (every transformation schedule is provably correct), but that is a *correctness* guarantee, not a *cost* guarantee. It explicitly treats "optimal relational algebra implementation" as a non-goal and drops at least one TPC-H query (Q13, outer join) as unsupported; it has no update/insert support, no LIMIT support, and runtime order-by/group-by/join/dedup are only partially foldable into the compiled form.
- **Bespoke OLAP (Wehrstein et al., 2026):** explicitly "sidesteps cost modeling entirely," selecting implementations by empirical benchmarking of sampled parameter instantiations rather than any cost model or bound, static or dynamic — [arXiv 2603.02001](https://arxiv.org/html/2603.02001v1). This directly confirms the gap: the most advanced closed-workload whole-engine-synthesis system found gives no compile-time guarantee at all, only after-the-fact measured performance with regression-rollback as the safety net.
- **Query-by-Synthesis / StatusQuo (Cheung, Solar-Lezama, Madden; PLDI 2013, CIDR 2013):** QBS (PLDI 2013) synthesizes SQL queries from application code fragments using program synthesis with a theory of ordered relations, evaluated on 75 fragments from >120k LOC of Hibernate ORM code with reported large speedups — [PLDI 2013](https://homes.cs.washington.edu/~akcheung/papers/pldi13.pdf). StatusQuo (CIDR 2013) uses program analysis to move functionality between application and database layers by translating imperative code into relational queries — [StatusQuo](https://people.eecs.berkeley.edu/~akcheung/papers/cidr13.html). Both optimize data access from application code but give no cost bound; they are about *correctness-preserving query extraction*, not cost guarantees or storage-layout co-design in the sense of Part 1/6's "automatic layout + bounded cost."
- **"Compiling Database Application Programs" (EPFL, arXiv 2018, 1807.09887):** argues for compiling application code together with the DB server for specialization/whole-program optimization — a conceptual precursor to Castor/Bespoke-OLAP-style whole-system compilation, but (per the search snippet; full text not fetched) does not claim compile-time cost bounds — [arXiv 1807.09887](https://arxiv.org/pdf/1807.09887).
- **Automatic Amortized Resource Analysis (AARA), surveyed in Hoffmann & Jost, "Two decades of automatic amortized resource analysis" (Math. Structures in Comp. Sci., received 2020):** a type-system-based static analysis that *does* derive provable worst-case resource bounds (time/heap-space) for first-order functional programs at compile time, reducing bound inference to linear-programming-style numeric optimization, with a soundness proof relative to an operational cost semantics — [survey PDF](https://www.cambridge.org/core/services/aop-cambridge-core/content/view/9A47A8663CD8A7147E2F17865C368094/S0960129521000487a.pdf/two-decades-of-automatic-amortized-resource-analysis.pdf). Extensions cover multivariate bounds (Hoffmann, Aehlig, Hofmann, TOPLAS 2012 — [PDF](https://www.cs.yale.edu/homes/hoffmann/papers/HAH12Toplas.pdf)), hybrid static+Bayesian bounds (PLDI/PACMPL vol. 8), ML-like programs with mutable references/arrays (FSCD 2017 — [Dagstuhl](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.FSCD.2017.26)), JavaScript, Rust (2025), and quantum circuits (2025). This is a real, mature body of compile-time worst-case cost-bound work — but this search found **no paper applying AARA, or an equivalent type-system-based static bound, to a database query language or a query engine's per-operation cost** (no hit for "query language" combined with AARA/resource-bound terms).
- **A 2016/2017 static resource-bound thesis applies tick-annotation-based static analysis to OCaml code that issues DynamoDB queries** (per search snippet of "Towards Automatic Resource Bound Analysis for OCaml," arXiv 1611.00692, and a related IISc thesis) — this is the single closest hit found to "static cost bound on a database call," but it bounds the *calling program's* resource use given DynamoDB calls as black-box-cost primitives; it does not bound or reject the *query itself* at compile time, and does not derive storage layout — [arXiv 1611.00692](https://arxiv.org/pdf/1611.00692).
- **Practical (non-formal) cost-based query rejection exists today, but only via the optimizer's cost *estimate*, not a proof:** Greenplum's `statement_cost` mechanism aborts a query if the optimizer's estimated cost exceeds a configured threshold (per a PostgreSQL mailing-list discussion) — [postgresql.org thread](https://www.postgresql.org/message-id/48968FBB.6040407%40paradise.net.nz); PostgreSQL's own community has resisted a built-in version of this because, as Tom Lane argued on the list, the cost estimates are known to be inaccurate, and client-side time limits were suggested instead — [postgrespro thread mirror](https://postgrespro.ru/list/thread-id/1122347). A 2025 US patent (US12386834B1) covers using "worst-case predicate selectivity" at compile/optimization time for query *plan* decisions (not rejection) — [Google Patents](https://patents.google.com/patent/US12386834); a separate older patent (US7058622) covers screening/rejecting queries before submission based on projected cost, conditioned on system backlog, not a provable bound — [USPTO PDF](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/7058622).
- **Robust query processing literature** pursues worst-case guarantees on *query plans* (bounding how badly a chosen plan can perform relative to cardinality-estimation error), which is adjacent but different from a compile-time bound on absolute cost or a full-scan rejection rule; search results only surfaced this as a line of work, without a specific paper/venue confirmed in this pass — flagged as a gap below.

### Inferences
- The field has the *tool* for formal compile-time worst-case cost bounds (AARA and its descendants) but has not — as far as this search can establish — pointed that tool at database query languages or query engines; the two threads (static program-cost analysis, and workload-compiled/specialized databases) appear not to have been connected in the literature surfaced here. Confidence: **medium-high** that no such connection exists in mainstream DB venues (SIGMOD/VLDB/CIDR/ICDE) 2018–2026, because repeated targeted searches for the combination returned only general-PL AARA papers and only one DB-adjacent analysis (the OCaml/DynamoDB resource-bound thesis, which bounds the caller, not the query); **low** confidence that it does not exist anywhere (e.g., in PL venues like PLDI/POPL/ICFP under a title that doesn't mention "database," or in a systems paper not indexed under the search terms tried).
- Every closed-workload engine-synthesis system found (Castor, Bespoke OLAP) treats cost as something to *measure and optimize empirically*, never something to *bound and enforce as a build-time guarantee/rejection rule*. This is a genuine, well-evidenced gap: the "reject at build time if a query would need a full scan, or synthesize an index instead" behavior described in the research objective does not exist in any system found — these systems either fall back to a slower general engine for unsupported queries (Bespoke OLAP) or simply fail to find a good (but still correct) layout (Castor), rather than issuing a build-time rejection with a cost proof.

### Gaps
- Did not find and could not confirm a specific paper on "robust query processing with worst-case plan-performance guarantees" (e.g., work by Babu/Garofalakis/Chaudhuri-style robust optimization) with a citable source in this pass — flagged as a likely-adjacent but unconfirmed area; would need a dedicated follow-up search (e.g., "robust query optimization worst-case guarantee Babu OR Markl OR Chaudhuri").
- Did not fetch the full text of "Compiling Database Application Programs" (arXiv 1807.09887) — only have the search-snippet-level description; its stance on cost bounds is unconfirmed (treated as a gap, not asserted as "no bounds").
- Did not find any 2018–2026 paper explicitly combining the phrase "compile-time" or "static" with "query rejection" or "index generation" as a build-time guarantee mechanism for a database system; the only rejection-like mechanisms found (Greenplum statement_cost, the two patents) are runtime/pre-execution heuristics based on optimizer estimates, not compile-time proofs tied to a closed workload.
- Did not independently verify whether AutoAdmin-style tuners, or the RL-based index advisors (AutoIndexer 2025, IA2, the Feb-2025 "New Paradigm in Tuning Learned Indexes" paper, the VLDB 2024 Huawei/Xiamen workload-knowledge paper), make any closed-workload assumption versus an open/continuously-sampled one — search snippets described them as operating on "a workload" or "sampled workload," consistent with Horticulture/Schism/AutoAdmin's sample-based (not provably closed/exhaustive) approach, but none of the fetched snippets used the words "closed" or "static" explicitly, so this should be treated as an inference, not a confirmed fact, for those specific 2023–2025 RL papers.
