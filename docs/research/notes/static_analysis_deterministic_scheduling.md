# Static Analysis of Transaction Programs and Deterministic, Lock-Free Parallel Transaction Scheduling

## What do Calvin, Bohm, PWV, Aria, Caracal, Q-Store, LADS, and other deterministic databases require, and how do they obtain read/write sets?

### Takeaway
Every deterministic/Calvin-style database needs *some* way to fix a global transaction order and know (or discover) data dependencies before or during a single pass of execution; the systems split into two families — (a) those that require the read/write set known in advance (Calvin, Bohm, VoltDB-style, original deterministic-locking designs) and use a client-side "reconnaissance" read phase when it isn't, and (b) newer systems (Aria, Caracal, PWV) that remove the a-priori requirement by executing speculatively against a snapshot and deterministically resolving conflicts afterward. None of them derive the read/write sets by static analysis of the transaction's own source code at build time — they either demand it be declared/known, or discover it dynamically at runtime (via a reconnaissance query or a speculative execution pass).

### Cited Findings
- Calvin (Thomson, Diamond, Weng, Ren, Shao, Abadi; SIGMOD 2012, DOI 10.1145/2213836.2213838) is a deterministic locking/scheduling and replication layer above storage that replicates transaction *inputs* rather than effects, eliminating distributed commit protocols. — [cs.princeton.edu PDF](https://www.cs.princeton.edu/courses/archive/fall19/cos418/papers/calvin.pdf)
- Calvin and prior deterministic systems must either know a transaction's full read/write set in advance or statically analyze the transactions beforehand; a 2026 retrospective blog post states these systems "assume transactions are non-interactive and that the read/write set is known before execution." — [muratbuffalo retrospective via scour.ing](https://scour.ing/@matmat/p/https://muratbuffalo.blogspot.com/2026/01/are-database-system-researchers-making.html)
- When a transaction's write set actually depends on a prior read (e.g., "look up by email, then update"), Calvin's own talk material describes handling this with an "optimistic lock location prediction" mechanism: a reconnaissance query is run first to discover which records will be touched, and the real transaction is submitted afterward with the discovered read/write set. — [Calvin slide deck](https://slidetodoc.com/calvin-fast-distributed-transactions-for-partitioned-database-based-7/)
- A 2026 blog review of deterministic databases (Calvin, SLOG, Detock) describes the general pattern as a "scout" or reconnaissance pattern: "the application run[s] a dry run read phase to optimistically build a write-set before sending it as a single atomic batch," and calls the claim that converting an app to this model needs "minimal changes" overly optimistic. — [muratbuffalo retrospective](https://scour.ing/@matmat/p/https://muratbuffalo.blogspot.com/2026/01/are-database-system-researchers-making.html)
- FaunaDB (built on Calvin's design, per a Jepsen analysis) "establishes a total order of transactions up front, then executes those transactions in parallel across all replicas," inheriting the a-priori-order requirement. — [Jepsen FaunaDB 2.5.4 analysis](https://jepsen.io/analyses/faunadb-2.5.4.pdf)
- Bohm (Faleiro & Abadi, VLDB 2015) is a pessimistic, serializable multi-version concurrency-control protocol: it analyzes a transaction's *write set* up front, fixes the serialization order, and pre-allocates version placeholders; reads never block and require no bookkeeping against contended writes. — [Aria PDF background via cs.arizona.edu](https://www.cs.arizona.edu/~caolei/papers/Aria.pdf) and [mohakchugh.is-a.dev summary](https://mohakchugh.is-a.dev/blog/aria-deterministic-database-scheduling-coordination-free-transactions)
- Aria (Lu, Yu, Cao, Madden; PVLDB 13(11), 2020, DOI 10.14778/3407790.3407808, "Aria: A Fast and Practical Deterministic OLTP Database") explicitly targets the limitation that "earlier deterministic databases require that transaction read/write sets are known before execution." It instead runs a *batch* of transactions speculatively against one snapshot (execution phase), then deterministically decides which commit (commit phase) without inter-replica communication, using a deterministic reordering heuristic to reduce conflicts. Reported results: up to 2x throughput over conventional non-deterministic concurrency control and over prior deterministic databases on YCSB and TPC-C on an 8-node cluster. — [cs.arizona.edu PDF](https://www.cs.arizona.edu/~caolei/papers/Aria.pdf); [DSpace@MIT record](https://dspace.mit.edu/handle/1721.1/133983)
- A follow-up critique (Gria, Frontiers of Computer Science, 2024) argues Aria is impractical to batch-size correctly "when the read-write set is unknown" and proposes refinements. — [journal.hep.com.cn Gria abstract](https://journal.hep.com.cn/fcs/EN/1159669497416179855)
- PWV ("Piece-Wise Visibility"; Faleiro, Abadi, Hellerstein, PVLDB 10(5), 2017, DOI 10.14778/3055540.3055546, "High Performance Transactions via Early Write Visibility") is a serializable concurrency-control protocol that restricts *when* a transaction may abort so that its writes can be made visible before the transaction finishes ("early write visibility"), isolating at finer-than-whole-transaction granularity. Reported gains: outperforms competing serializable protocols by up to an order of magnitude and Read Committed by up to 3x under high contention. — [NSF Public Access PDF](https://par.nsf.gov/servlets/purl/10156624)
- Caracal (Qin, Demke Brown, Goel — University of Toronto) is a shared-memory, main-memory deterministic database aimed at skewed/contended workloads: it batches transactions into epochs, *analyzes the batch* to find contended keys, and splits some transactions into a contended piece and an uncontended piece. Reported gains: 1.9x–9.7x over prior deterministic schemes on most workloads. — [eecg.utoronto.ca PDF](https://www.eecg.utoronto.ca/~ashvin/publications/caracal.pdf). Note: I could not confirm the exact venue/year from search snippets (my own prior knowledge, not independently verified here, places it at SIGMOD 2021 — flag as unverified).
- Q-Store: could not find the original Q-Store paper's venue/year directly. A related 2021 arXiv paper on "QR-Store" (Qadah & Sadoghi) describes Q-Store as a "queue-oriented" deterministic transaction-processing design the authors built on, reporting up to 22x throughput improvement over "state-of-the-art deterministic transaction processing systems" in a Purdue dissertation by the same group. — [arXiv:2107.11378](https://arxiv.org/pdf/2107.11378); [Purdue dissertation](https://docs.lib.purdue.edu/dissertations/AAI30505107)
- LADS: no source found describing a deterministic database called "LADS" (searches for "LADS label-based deterministic database SIGMOD" and "LADS ... SIGMOD 2023" returned no matching paper). This is a confirmed gap, not a negative finding about the system's content.
- VoltDB (H-Store lineage): partitions data across single-threaded execution engines, each with exclusive access to its partition, avoiding locks/latches/logging overhead for single-partition work; multi-partition transactions are coordinated sequentially through a Multi-Partition Initiator (MPI), and stored procedures must be deterministic (checked by hashing/comparing resulting SQL across replicas) so execution can be pipelined given a consensus on order. — [VoltDB docs](https://docs.voltdb.com/UsingVoltDB/IntroHowVoltDBWorks.php); [Jepsen VoltDB 6.3 analysis](https://jepsen.io/analyses/voltdb-6-3); [Wikipedia VoltDB](https://en.wikipedia.org/wiki/VoltDB)
- Lotus (PVLDB 15, 2022, "Scalable Multi-Partition Transactions on Single-Threaded...") argues the H-Store/VoltDB single-threaded-partition concurrency scheme can be improved for multi-partition workloads. — [vldb.org PDF](https://www.vldb.org/pvldb/vol15/p2939-zhou.pdf)

### Inferences
- The field's trajectory (Calvin → Bohm → PWV → Aria → Caracal → Gria/ForeSight) is a progressive *relaxation* of the a-priori read/write-set requirement, moving from "declare before execution" to "discover via one speculative/snapshot execution pass, then deterministically reconcile" — but none of this progression substitutes compile-time static analysis of the transaction's source code for either declaration or runtime discovery.
- The "reconnaissance query" / "scout" pattern used for Calvin-style dependent reads (lookup-by-email-then-update) is a *runtime* mechanism (an actual query is executed against live data to discover the read set) rather than a static, build-time derivation — this is a structurally different approach than compiling the transaction function and deriving its access pattern as a function of its *parameters* without touching live data.

### Gaps
- Could not verify Caracal's or Q-Store's exact publication venue/year from primary sources within the search budget; only secondary mentions were found.
- Could not find any source describing a system named "LADS" matching the deterministic-database description in the brief — possibly a different acronym expansion, a very recent (2024-2026) paper not yet well-indexed, or a different field; flagging this as an open gap rather than asserting it doesn't exist.

## What do static-analysis approaches do (chopping, IC3, Callas, Runtime Pipelining, Lynx, Transaction Repair, Cheung/Xie, blockchain executors)?

### Takeaway
The pre-2018 static-analysis line (Shasha's chopping, Amato et al.'s abstract interpretation, IC3, Callas/MCC) analyzes a *fixed, known set of transaction programs* ahead of time to build a conflict/precedence graph and thereby licenses more concurrency than naive locking — but this analysis targets the *given, finite workload of stored-procedure-like programs*, not a general build pipeline that compiles arbitrary application code and derives per-call read/write sets as a function of runtime parameters. Blockchain parallel executors (Block-STM, Sealevel, Sui) achieve deterministic, parallel, lock-free execution but do so either by *runtime* optimistic re-execution with validation (Block-STM) or by requiring the *transaction author* to declare accessed accounts/objects up front (Sealevel, Sui) — again, not by compiling the program and statically deriving its access set.

### Cited Findings
- Transaction chopping (Shasha, Llirbat, Simon, Valduriez; the foundational 1995 ACM TODS work) splits each transaction into smaller pieces to shorten lock-hold time; correctness is checked *before runtime* using a statically-built "SC-graph" over the pieces (sibling edges within a transaction, conflict edges across transactions); the chopping is valid only if the SC-graph has no cycle, and only the first piece of a chopped transaction may abort. — [cs.nyu.edu PDF](https://cs.nyu.edu/~shasha/papers/chopping.pdf); [Academia.edu summary](https://www.academia.edu/127540228/Transaction_chopping)
- IC3 ("Scaling Multicore Databases via Constrained Parallel Execution," Wang, Mu, Cui, Yi, Chen, Li; SIGMOD 2016) pairs *static analysis of the transaction workload* with *runtime tracking of dependencies* between concurrently running transactions, refining chopping with column-level static analysis to reduce false conflicts; it tracks dependencies at runtime and enforces ordering on pieces connected by conflict edges to preserve serializability. Reported: ~434K TPS on single-warehouse TPC-C on a 64-core machine, beating traditional schemes under contention. — [NYU TR2016-981 PDF](https://cs.nyu.edu/media/publications/TR2016-981.pdf)
- Polyjuice (arXiv 2105.10329) uses IC3 as a baseline and notes IC3 permits some reads to be "dirty"; it replaces IC3's hand/static-designed interleaving policy with a *learned* concurrency-control policy. — [arXiv:2105.10329](https://arxiv.org/pdf/2105.10329)
- Callas (Xie, Su, Littley, Alvisi, Kapritsos, Wang; SOSP 2015 — NOT VLDB, correcting the brief's framing) introduces "modular concurrency control" (MCC): it statically partitions the transaction workload into groups so an isolation property enforced inside each group composes into a system-wide guarantee; reported 8.2x throughput gain on TPC-C over a MySQL Cluster baseline "without any programming effort." — [cs.utexas.edu PDF](https://www.cs.utexas.edu/~lorenzo/papers/Chao15Callas.pdf)
- Amato, Giannotti, Mainetto (VLDB 1993) is the earliest found instance of *automatically* deriving read/write-set approximations from transaction source code via abstract interpretation (non-standard/abstract interpretation of a subset of the Galileo persistent language), feeding a scheduler that implements conservative two-phase locking. The analysis is conservative (an over-approximation), computed in finite time, from "the text of a transaction and a representation of the data stored in the database." — [vldb.org 1993 PDF](https://www.vldb.org/conf/1993/P405.PDF)
- Dias, Lourenço, Preguiça (2011, extending the chopping/static-analysis line to Snapshot Isolation) extract compact read/write sets per transaction, build a static dependency graph, and check whether concurrent execution is serializable under SI; their StarTM tool uses shape analysis with separation logic to detect write-skew anomalies in Java STM programs, with explicit false-positive risk acknowledged by the authors. — [sites.fct.unl.pt PDF](https://sites.fct.unl.pt/synergy-vm/files/ddls11.pdf)
- "Transaction Repair" / MV3C (SIGMOD 2017, "Transaction Repair for Multi-Version Concurrency Control") re-executes only the *conflicting part* of a transaction (using a dependency graph) rather than aborting and restarting the whole transaction; the authors say "lightweight dependency data from manual or static analysis keeps overhead low," with large gains under high contention. A related patent (US11372837) states that "when dependencies can be found in advance with static analysis, ordering reads before writes can eliminate repair for those items." — [rmarcus.info summary](https://rmarcus.info/dbscholar/papers/hd6eb93859aad568a); [Google Patents US11372837](https://patents.google.com/patent/US11372837)
- Program-analysis-for-concurrency-control line (distinct from Cheung/Xie specifically, which I could not confirm as a named paper pair): Deshmukh, Ramalingam, Ranganath, Vaswani, "Logical Concurrency Control from Sequential Proofs" (arXiv 1107.4422) synthesizes concurrency-control code for a library from a sequential correctness proof, guaranteeing correctness when the library is invoked by arbitrary concurrent clients. — [arXiv:1107.4422](https://arxiv.org/pdf/1107.4422)
- Block-STM (Aptos/Diem lineage; arXiv 2203.06871) is a parallel smart-contract execution engine built on Software Transactional Memory: it executes a block's transactions speculatively on multiple threads while preserving the outcome of a fixed, preset serial order, using a low-overhead collaborative scheduler for execution/validation tasks and multi-version concurrency control for versioned writes; every transaction records its own read-set and write-set *during (speculative) execution*, and conflicting transactions are re-executed — this is runtime discovery, not static/build-time derivation. — [arXiv:2203.06871](https://web3.arxiv.org/abs/2203.06871v3); [Aptos Foundation write-up](https://aptosfoundation.org/currents/aptos-ecosystem-leading-the-way-with-parallelism)
- Solana Sealevel requires transactions to *declare in advance* which accounts they will read and write; the runtime applies read/write locks to the declared accounts and schedules transactions whose writable sets don't overlap to run concurrently across cores; anything not declared is off-limits to the transaction. Conflicting transactions (same account) execute sequentially; ordering of non-conflicting transactions within a slot is non-deterministic. — [GridPlus docs](https://docs.gridplus.io/blockchain-basics/solana/accounts-sealevel-and-the-spl); [Zealynx glossary](https://www.zealynx.io/glossary/sealevel)
- Sui's object model ties the execution path to object ownership: objects owned by a single user/address can bypass full BFT consensus for near-instant finality and execute in parallel; a transaction touching any *shared* object goes through BFT consensus; child objects inherit their parent's execution path. This is a declared-ownership model, not a derived-from-code model. — [Move Book, "Fast Path and Consensus"](https://move-book.com/object/fast-path-and-consensus.md); [BitGo Sui write-up](https://www.bitgo.com/en-ae/resources/blog/launching-support-for-sui)

### Inferences
- Across both the academic static-analysis line (chopping → IC3 → Callas) and the blockchain line (Sealevel, Sui), "static" in practice means one of two things: (1) analysis of a *fixed, finite, known-in-advance set of transaction programs/stored procedures* to build a precedence graph that a runtime scheduler then enforces, or (2) a *declaration contract* the transaction author must satisfy (Sealevel's declared accounts, Sui's object ownership) — never a compiler pass over arbitrary transaction code that derives the read/write set as a function of the transaction's *parameters* at *build time*, independent of a fixed workload set.
- Block-STM's "deterministic, lock-free, abort-... " framing is the closest *mechanism* match to the candidate database's stated goal (deterministic, lock-free parallel schedule, serializable isolation) among the surveyed systems, but it is abort-based (speculative re-execution on conflict) rather than abort-free, and it discovers read/write sets at runtime via execution, not via static analysis of compiled code.
- "Lynx" and "Runtime Pipelining," both named explicitly in the brief, could not be matched to a specific, verifiable paper (see Gaps) — the only "Lynx" found (NYU/Microsoft Research, Zhang et al. 2013, "Transaction chains: achieving serializability with low latency in geo-distributed storage systems") uses static analysis to determine whether transaction *chain hops* can execute independently while preserving serializability, which is topically adjacent but is about geo-distributed chain decomposition, not deterministic core-parallel scheduling; treat any claim tying this Lynx to the brief's intended system as unconfirmed.

### Gaps
- Could not locate a specific "Runtime Pipelining" deterministic-database paper (search for Faleiro + pipelining + deterministic + multicore did not surface it); it is possible this refers to a 2022 PVLDB paper by Helt, Sharma, Abadi, Lloyd, Faleiro ("C5" or a related cloned-concurrency-control paper) that appeared in the same search results, but I could not confirm the title or content match, so I am not reporting it as a finding.
- Could not confirm whether "Cheung" and "Xie" in the brief refer to Alvin Cheung (UC Berkeley, program synthesis/verified lifting for database applications) and Chao Xie (Callas/MCC, SOSP 2015) specifically, or to a joint/different paper; Alvin Cheung's Berkeley profile confirms his general research area (program analysis/synthesis for database applications, "verified lifting") but no specific paper pairing him with Xie on concurrency-control program analysis was found. Flag as unverified attribution.
- Could not confirm Lynx's deterministic-database identity as distinct from the geo-distributed transaction-chains system found.

## Does any system derive read/write sets automatically from compiled transaction code at build time, for a deterministic parallel schedule? How are dependent reads handled?

### Takeaway
No system found in this research derives read/write sets by static analysis of *compiled* transaction code at *build time* and then uses that analysis to drive a deterministic, lock-free, abort-free parallel schedule with serializable isolation. The closest precedent for automatic, code-derived read/write-set approximation is Amato, Giannotti & Mainetto (VLDB 1993) — but it is runtime/scheduler-facing abstract interpretation for an interpreted language (Galileo), not a build-time compilation step, predates all the deterministic-database literature by two decades, and was not picked up by the Calvin/Bohm/Aria lineage. Dependent reads (read-then-decide-what-to-write, e.g., lookup-by-email-then-update) are universally handled either by (a) a runtime reconnaissance/scout query that physically executes against live data before the "real" transaction is scheduled (Calvin-style), or (b) speculative execution against a snapshot with deterministic conflict resolution and possible re-execution (Aria, Block-STM) — never by a static, build-time derivation of the dependent access as a function of parameters alone, because the dependent read's result is genuinely unknowable without touching current data.

### Cited Findings
- Amato, Giannotti, Mainetto (VLDB 1993): "This interpreter, given the text of a transaction and a representation of the data stored in the database, automatically derives in a finite time an approximation of the read-set and write-set of the analysed transaction... information from the non-standard interpretation is passed to the scheduler before execution starts, yielding a scheduler that implements a conservative two-phase locking protocol." This is the one source found that matches the shape of "derive read/write sets from code, feed a scheduler" — but note it targets conservative 2PL scheduling, not a deterministic lock-free parallel schedule, and the approximation is necessarily conservative (over-approximating), which is a structurally different trade-off than an exact, parameter-indexed read/write-set function. — [vldb.org 1993 PDF](https://www.vldb.org/conf/1993/P405.PDF)
- Calvin's handling of dependent reads: per Calvin's own presentation materials, a transaction whose full read/write set depends on a prior read runs an "optimistic lock location prediction" — a reconnaissance query executed first to discover the actual read/write set, after which the transaction is submitted with that discovered set. — [Calvin slide deck](https://slidetodoc.com/calvin-fast-distributed-transactions-for-partitioned-database-based-7/)
- A 2026 retrospective explicitly frames this as a weakness: the reconnaissance/"scout" read can go stale by the time the main transaction executes (noted independently for the related Prognosticator paper on reconnaissance staleness), and converting an arbitrary application to this model is "not minimal changes" as sometimes claimed. — [muratbuffalo retrospective](https://scour.ing/@matmat/p/https://muratbuffalo.blogspot.com/2026/01/are-database-system-researchers-making.html); [Prognosticator, ICDCS 2020 PDF](https://www.dpss.inesc-id.pt/~praminhas/papers/ICDCS2020.pdf)
- Aria avoids the a-priori requirement differently: it executes transactions speculatively against a shared snapshot without knowing read/write sets in advance, then deterministically decides which to commit in a conflict-free, communication-free way across replicas — this works for dependent reads because the *speculative execution itself* performs the lookup; the novelty is in the deterministic *commit-decision* rule, not in predicting the access pattern before execution. — [cs.arizona.edu Aria PDF](https://www.cs.arizona.edu/~caolei/papers/Aria.pdf)
- Block-STM's read/write sets are recorded "during execution" (i.e., at runtime, per actual speculative execution), explicitly not derived ahead of time; a conflicting transaction is simply re-executed. — [arXiv:2203.06871](https://web3.arxiv.org/abs/2203.06871v3)

### Inferences
- The candidate database's part 3 — compiling transaction functions at build time and statically deriving read/write sets *as functions of their parameters* — appears to be a materially different mechanism from everything found: it is not "known/declared read-write set" (Calvin/Bohm/Sealevel/Sui), not "discovered via one runtime execution pass" (Aria/Block-STM/Caracal), and not "approximated by abstract interpretation of an interpreted/dynamic language at runtime, feeding a lock scheduler" (Amato et al. 1993). The specific combination — ahead-of-time compilation, parametric (not merely workload-level) read/write-set derivation, and a deterministic *lock-free and abort-free* (not merely deterministic-commit or speculative-with-reexecution) parallel schedule with serializable isolation — was not matched by any single prior-art source in this research pass. This should be treated as a plausible-but-not-exhaustively-proven novelty claim: it rests on the absence of a hit across a reasonably thorough but time-boxed search, not on a systematic literature review (e.g., no full-text read of ACM Digital Library venues, no DBLP crawl).
- Dependent reads (lookup-then-decide) remain the hardest open case for *any* static/ahead-of-time scheme, prior art included: every system that handles them resorts to a genuine runtime step (reconnaissance query or speculative execution) precisely because the dependent write target is a function of *data*, not just of the call's static parameters. A static-analysis system that only derives read/write sets as functions of a transaction's *parameters* (not of data read during execution) would, by construction, be unable to handle this class unless it (a) restricts the transaction language so that dependent reads are expressed as declared index lookups whose result set is treated as the write set's possible targets (an over-approximation, similar in spirit to Amato et al.), or (b) falls back to a runtime reconciliation step for exactly this class, which would itself need documenting as a boundary case/limitation of the architecture under review, not a solved problem.

### Gaps
- This research pass did not include a systematic DBLP/ACM-DL crawl of the "static program analysis + OLTP concurrency control" area 2018-2026; it is possible a 2023-2026 paper exists that performs build-time, parametric read/write-set derivation from compiled transaction code and was simply not surfaced by the search queries used (the queries returned mostly older or adjacent work). Flagging this explicitly: absence of evidence here is evidence of a gap in this search, not strong evidence of absence in the literature.
- No source was found that discusses how a parametric (as opposed to workload-level) static read/write-set derivation would specifically compose with secondary indexes or non-key lookups (the "lookup by email" case) at build time; this is a genuine open question the report should flag as unresolved by prior art rather than resolved in some specific way.

## What are the measured throughput gains and known failure modes (skew, hot keys, long transactions, dependent reads)?

### Takeaway
Measured throughput gains for deterministic/speculative schemes range roughly 1.9x-9.7x over prior deterministic baselines (Caracal) and up to ~2x over non-deterministic baselines (Aria), with newer skew-aware designs (ForeSight) claiming up to 2x over Aria specifically under skew; but every one of these systems documents sharp throughput degradation under skew/hot-key contention and high abort rates as its primary failure mode, and none of the sources found reports results for long-running transactions or deep dependent-read chains as a distinct, separately-measured failure mode — only hot-key/skew and abort-rate-under-contention are consistently measured.

### Cited Findings
- Aria: reports up to 2x throughput over conventional non-deterministic concurrency control and prior deterministic databases on YCSB/TPC-C (8-node cluster), but a TU Delft thesis evaluating Aria found it "suffers under high contention because of high abort rates," and that lowering isolation to snapshot isolation or reordering transactions by degree each reduces aborts (with reordering also cutting latency). — [cs.arizona.edu PDF](https://www.cs.arizona.edu/~caolei/papers/Aria.pdf); [TU Delft Aria thesis](https://repository.tudelft.nl/file/File_aac98a19-b324-4e63-8883-177bf0c1f694)
- Caracal: reports 1.9x-9.7x gains over prior deterministic schemes on most workloads, specifically engineered to address skewed/contended workloads by splitting contended transactions into separately-handled pieces. — [eecg.utoronto.ca PDF](https://www.eecg.utoronto.ca/~ashvin/publications/caracal.pdf)
- ForeSight (arXiv 2508.17375, 2025): under a 0.999 skew factor, ForeSight retains ~76% of its no-skew throughput versus Aria's ~34%, crediting conflict prediction for reduced contention-related aborts; headline claim is up to 2x higher throughput than Aria specifically on skewed workloads. — [arXiv:2508.17375](https://arxiv.org/pdf/2508.17375)
- HarmonyBC (arXiv 2211.15163, a private-blockchain-meets-deterministic-database system): evaluated on Smallbank/YCSB with varying skew and a hotspot-resiliency test (1% of records hot); aborts rise with skew across all compared systems, and the paper attributes its own lower abort rate to its handling of write-write dependencies compared to AriaBC/RBC baselines, which abort more on those. — [arXiv:2211.15163](https://arxiv.org/pdf/2211.15163)
- IC3 (SIGMOD 2016): reports ~434K TPS on single-warehouse TPC-C on a 64-core machine, specifically framed as beating traditional (2PL/OCC) schemes "under contention" — i.e., its headline win is contention/hot-key robustness, not raw uncontended throughput. — [NYU TR2016-981 PDF](https://cs.nyu.edu/media/publications/TR2016-981.pdf)
- Callas/MCC (SOSP 2015): reports 8.2x throughput gain on TPC-C over a MySQL Cluster baseline "without any programming effort," but the search did not surface a skew/hot-key-specific breakdown for this result. — [cs.utexas.edu PDF](https://www.cs.utexas.edu/~lorenzo/papers/Chao15Callas.pdf)
- PWV (PVLDB 2017): reports up to an order-of-magnitude improvement over competing serializable protocols and 3x over Read Committed "under high contention" specifically — again, the reported win is explicitly scoped to the contended regime. — [NSF Public Access PDF](https://par.nsf.gov/servlets/purl/10156624)

### Inferences
- The consistent framing across sources — every reported throughput multiplier is qualified by "under contention" or "under skew" — suggests the research community treats skew/hot-key resilience as *the* central differentiator between deterministic-scheduling designs; uncontended throughput is treated as a solved, less-differentiating case.
- No source in this pass separately isolates "long transactions" as a measured failure mode (distinct from general contention/skew); this is likely because in the deterministic-database literature, a long transaction's main cost is the time it holds up a batch/epoch or blocks pipelining (a latency/throughput coupling issue), which the sources discuss only implicitly via epoch-based batching designs (Aria's batch, Caracal's epoch) rather than as an explicitly labeled "long transaction" benchmark axis.

### Gaps
- No quantified data found on dependent-read chains (e.g., multi-hop lookup-then-decide transactions) as a distinct benchmark axis in any of the surveyed papers; TPC-C and YCSB/Smallbank — the benchmarks actually used — do contain some dependent-access patterns implicitly (e.g., TPC-C's "payment" transaction can look up a customer by last name), but none of the sources reports a result broken out specifically for that case.
- Could not find explicit abort-rate or throughput numbers for long-running transactions specifically (as opposed to contended/skewed short transactions) in any deterministic-database paper surveyed here.

## Status of Turso/Limbo (Rust rewrite of SQLite) MVCC and concurrent writes, and VoltDB's single-threaded partitions, as reference points

### Takeaway
Turso (the Rust, clean-room rewrite of SQLite formerly codenamed "Limbo") shipped MVCC-based concurrent writes on Turso Cloud as of August 3, 2026, exposed via a `BEGIN CONCURRENT` mode that does row-level conflict detection at commit (returning `SQLITE_BUSY` on write-write conflicts, requiring application-level retry) and supports up to 16 concurrent writers in its documented example; this is optimistic/abort-based concurrency, not deterministic lock-free scheduling. VoltDB, by contrast, is the classic abort-free reference point: single-threaded execution engines per partition with no locks/latches, deterministic stored procedures required (verified by hashing/comparing resulting SQL across replicas), and multi-partition work serialized through a coordinator (MPI) at a throughput cost that grows with node count.

### Cited Findings

- Turso's own blog states concurrent writes on Turso Cloud shipped August 3, 2026, exposed as `BEGIN CONCURRENT`; per the docs, "Concurrent" mode is MVCC-only and performs row-level conflict detection at commit, returning `SQLITE_BUSY` on write-write conflicts that the application must retry; the documented example supports up to 16 concurrent writers. — [Turso blog: "Concurrent Writes in Practice"](https://turso.tech/blog/concurrent-writes-in-practice)
- A July 2025 mirror of the repository still listed `BEGIN CONCURRENT`/MVCC as a roadmap item ("improved write throughput using multi-version concurrency control"), confirming the feature is recent (shipped between mid-2025 and August 2026). - VoltDB: each partition is handled by exactly one single-threaded execution engine assigned to one core, with exclusive access to that partition's data; VoltDB's own documentation states this design "ensures transactional consistency without the overhead of locking, latching, and transaction logs." Wikipedia: "no physical locks or latches are included in the system," and "once a transaction is started, it cannot stall waiting for another transaction to complete." — [VoltDB "How VoltDB Works" docs](https://docs.voltdb.com/UsingVoltDB/IntroHowVoltDBWorks.php); [VoltDB Wikipedia](https://en.wikipedia.org/wiki/VoltDB)

- Lotus (PVLDB 15, 2022) explicitly frames itself as improving on the H-Store/VoltDB single-threaded-partition scheme specifically for *multi-partition* workloads, implying this remains VoltDB's acknowledged weak point as of 2022. — [vldb.org PDF](https://www.vldb.org/pvldb/vol15/p2939-zhou.pdf)

### Inferences
- Turso's `BEGIN CONCURRENT` is architecturally the opposite reference point from the candidate database's goal: it is optimistic/abort-and-retry MVCC (the application must handle `SQLITE_BUSY` retries), not deterministic/lock-free/abort-free scheduling — useful in the report as a contrast case showing what "concurrent writes without a static schedule" costs in practice (explicit conflict detection at commit, bounded concurrent-writer count of 16 in the documented example, "experimental" status as recently as November 2025).
- VoltDB remains the closest *abort-free* reference point among all systems surveyed in this entire research pass (not just this section) precisely because it sidesteps the general problem: it achieves determinism and lock-freedom by requiring stored procedures to be single-partition and by serializing (not parallelizing) the multi-partition case through a coordinator — i.e., it does not solve cross-partition parallel deterministic scheduling, it avoids the problem by partitioning and penalizing the cross-partition case. This is a meaningful contrast point for the candidate database's part 3 if it claims to handle multi-key/cross-partition transactions in a lock-free deterministic parallel schedule, since VoltDB explicitly does not.
